계정·계산 노드·공유 저장소를 관리하는 담당자를 위한 문서입니다. 일반적인 접속과 계산 방법은 사용자 안내에서 확인할 수 있습니다.

일상 점검

대상 확인할 내용
서버 접속 가능 여부, 시간, CPU 부하, 메모리
저장소 용량·inode, 마운트, 사용자 쓰기 권한, quota
계산 노드 OS 부팅, 인증, 프로그램 접근, 하드웨어 오류
고속망 링크 상태·속도, 실제 병렬 통신
스케줄러 사용 시 서비스·노드 상태, 실제 시험 작업

기본 확인 명령입니다. 존재하는 기능과 현장 정책에 맞춰 사용합니다.

hostname
uptime
free -h
df -hT
findmnt -t nfs,nfs4
systemctl --failed

서비스가 실행 중이라는 표시만으로 전체 상태를 판단하지 않습니다. 개인 사용자 계정의 접속·파일 쓰기·작은 계산까지 확인합니다. BMC 전원 On과 OS 부팅 성공도 구분합니다.

사용자 계정

사용자 추가 전 UID/GID 충돌, 프로젝트 그룹, 사용 기간, 저장 공간·quota를 확인합니다. 실제 인증 체계에 맞춰 계정을 생성하고 계산 노드의 계정 매핑과 인증도 반영합니다.

추가 후에는 해당 사용자의 접속·공유 경로 쓰기·프로그램 실행을 시험합니다. 비밀번호나 개인 SSH 비밀키를 공용 설정 파일에 넣지 않습니다.

계정 사용 종료 시 모든 인증 경로와 실행 중 작업을 확인합니다. 계정 비활성화와 홈·프로젝트 데이터 삭제는 분리하여 처리하고 보존 정책·소유자 확인을 거칩니다.

프로그램·라이브러리 추가

공용 응용프로그램은 모든 대상 노드가 같은 경로로 사용할 수 있도록 구성합니다. OS 라이브러리는 필요한 로그인 서버와 계산 노드 이미지에 각각 반영합니다.

RAM 기반 계산 노드에서는 실행 중인 노드에만 설치한 변경이 재부팅 후 사라질 수 있습니다. 영구 이미지·overlay·구성 관리 대상도 함께 갱신해야 합니다.

  1. 적용할 프로그램·버전·노드와 점검 시간을 정합니다.
  2. 변경 대상과 승인된 범위의 이전 설정을 보관하고 복구 방법을 정합니다.
  3. 사용하는 배포 도구의 버전에 맞춰 영구 구성을 변경합니다.
  4. 시험 노드를 새 구성으로 부팅하고 인증·마운트·실행 환경을 확인합니다.
  5. 작은 단일 노드 계산 후 필요한 멀티노드·고속망·라이선스 시험을 진행합니다.
  6. 정상 확인 후 나머지 노드에 적용합니다.

Warewulf 3의 wwsh·wwvnfs와 Warewulf 4의 wwctl은 관리 방식이 다릅니다. 다른 버전의 명령을 그대로 혼용하지 않습니다. 커널·GPU·RDMA 변경은 제품이 지원하는 조합을 먼저 확인합니다.

공유 저장소

NFS 공유 대상은 필요한 호스트·관리망으로 제한하고 기본적으로 root_squash를 유지합니다. 공유 경로·사용자 그룹·읽기/쓰기·quota 정책을 함께 확인합니다.

공유 설정 변경 후 서버의 exports와 클라이언트의 실제 마운트를 확인하고, 일반 사용자로 파일 생성·읽기를 시험합니다. 마운트 변경도 영구 계산 노드 구성에 반영해야 합니다.

재부팅과 유지보수

사용자와 점검 시간을 조정하고 새 작업이 시작되지 않도록 한 뒤 실행 중 작업을 확인합니다. 직접 실행 환경에서는 w나 squeue만으로 작업이 없다고 판단하지 않습니다. 실제 프로세스·응용프로그램 상태와 예약 기록을 함께 확인합니다.

Slurm을 사용하는 노드는 현장 절차에 따라 새 작업을 차단하고 작업 종료를 기다립니다. 직접 실행과 병행한다면 직접 작업도 따로 확인해야 합니다. 정상 종료·재부팅을 우선하고, 복귀 후 사용자 작업이 가능한지 검증합니다.

전체 정지·기동은 저장소와 핵심 서비스의 의존 관계에 따라 수행합니다. 현장의 인수 자료에 기재된 순서와 복구 절차를 사용하세요.

장애 확인 순서

증상 우선 확인
노드가 부팅되지 않음 전원·POST·하드웨어 이벤트 → NIC → DHCP·PXE → 커널·이미지 → 마운트
SSH 접속 실패 접속 경로 → 서비스·방화벽 → 호스트 키 → 계정·인증
파일 쓰기 실패 저장소·마운트 → 용량·quota → UID/GID·그룹·권한
병렬 계산 실패 단일 노드 실행 → 라이선스·경로·인증 → MPI·고속망 → 멀티노드 실행

과거 하드웨어 이벤트와 현재 오류를 구분하여 기록합니다. 반복적인 전원 조작이나 설정 초기화보다 발생 시각·대상 노드·로그·재현 조건을 먼저 확보합니다.

운영 기록과 지원 요청

현장 구성표에 소프트웨어 버전, 이미지·노드 대응, 공유 경로, 인증 방식, 서비스·로그 위치, 변경 내역과 복구 절차를 유지합니다. 접속 인증 정보는 승인된 별도 방식으로 보관합니다.

지원 요청 시에는 영향 범위, 시작 시각, 변경 이력, 오류 메시지, 지금까지 확인한 내용을 함께 전달합니다. 사용자 데이터나 인증 정보를 로그에 포함해야 하는 경우 먼저 전달 범위를 확인합니다.

사용자 계정 추가·동기화·제거

이 장의 변경 명령은 관리 노드에서 권한 있는 담당자가 실행합니다. 로컬 파일 기반과 LDAP/AD/SSSD 같은 중앙 인증 방식을 구분합니다. 아래 예제의 YOUR_*는 승인된 실제 값으로 바꿉니다.

1. 추가 전 확인

사용자명·UID·기본 그룹·보조 그룹·사용 기간·프로젝트·저장 공간을 승인받습니다. 모든 노드와 저장소에서 UID/GID가 일관되어야 합니다.

getent passwd YOUR_USER
getent passwd YOUR_UID
getent group YOUR_GROUP

이미 있는 사용자·UID·그룹을 덮어쓰지 않습니다. 중앙 인증 사용자는 디렉터리 서비스에서 관리하고 동일 이름의 로컬 계정을 임의로 만들지 않습니다.

2. 로컬 사용자 예제

기본 그룹이 준비된 경우:

useradd -m -u YOUR_UID -g YOUR_GROUP -s /bin/bash YOUR_USER
passwd YOUR_USER
id YOUR_USER
getent passwd YOUR_USER

기본 그룹도 새로 만들 필요가 있으면 승인된 미사용 GID로 groupadd -g YOUR_GID YOUR_GROUP을 먼저 수행합니다. 비밀번호는 프롬프트나 승인된 초기 인증 전달 방식으로 설정합니다. 공용 문서·명령 인수에 비밀번호를 넣지 않습니다.

3. 계산 노드 계정 매핑

인증 방식에 맞춰 passwd/group의 사용자 매핑, SSH 공개키·인증 서비스·PAM 정책, 홈 마운트와 그룹 권한을 반영합니다. 마스터의 시스템 계정 파일을 통째로 덮어쓰면 이미지의 서비스 UID/GID와 충돌할 수 있습니다. 신규 계정만 반영하거나 충돌을 검증한 관리 파일을 사용합니다.

Warewulf 3에서 이미 등록·할당된 배포 파일을 갱신하는 형태입니다. 먼저 파일 목록과 각 노드 배포 대상을 확인합니다.

wwsh file list
wwsh provision print YOUR_NODE
wwsh file resync

resync가 어떤 등록 파일을 갱신하는지 먼저 검토합니다. shadow·gshadow·비밀키를 무조건 배포하는 절차로 사용하지 않습니다. 이미지의 재부팅 후 상태와 실행 중 노드의 갱신을 따로 확인합니다. 현장에 wwgetfiles가 구성된 경우 갱신 주기를 기다리거나 승인된 수동 갱신 절차를 사용합니다. 캐시 디렉터리의 무차별 삭제는 기본 절차로 넣지 않습니다.

여러 노드 조회에 pdsh가 제공되는 경우:

pdsh -R ssh -w 'YOUR_APPROVED_NODE_RANGE' 'hostname; getent passwd YOUR_USER'

호스트 범위 확장 형식과 실제 대상 목록을 확인합니다. root 키의 호스트 검증을 끄거나 관리자 비밀키를 노드에 배포하지 않습니다. Warewulf 4는 해당 버전의 syncuser·overlay 관리 방식을 사용합니다.

4. 인수 시험

해당 사용자로 실제 로그인·계산 노드 접근·공유 폴더 생성·파일 소유권·그룹 공유·프로그램 실행을 확인합니다. Slurm 회계를 쓰면 사용자·Account·Association·허용 QoS도 별도로 등록·검증합니다. OS 계정 생성만으로 Slurm 프로젝트 권한이 자동 생성된다고 가정하지 않습니다.

5. 계정 비활성화와 제거

실행 중 직접 작업·Slurm 작업, 공동 프로젝트 파일·예약·자동 실행을 조사합니다. 승인에 따라 비밀번호·SSH 키·중앙 인증·접속 정책 등 실제 인증 경로를 차단합니다. usermod -L 같은 비밀번호 잠금만으로 키 로그인까지 막히는 것은 아닙니다.

보존 정책과 인수인계를 확인한 후 로컬 계정을 제거하는 형태입니다.

userdel YOUR_USER

이 예제는 홈 삭제 옵션을 사용하지 않습니다. 사용자 데이터 삭제·소유권 이전·UID 재사용은 별도 판단·승인 후 수행합니다. 계산 노드·이미지·인증 서비스·Slurm의 관련 권한도 동기화하고 재로그인·재부팅 후 상태를 확인합니다.

1. 변경 위치 결정

공유 프로그램 설치와 OS 라이브러리 설치를 구분합니다. 응용프로그램은 승인된 공유 트리에 버전별로 설치할 수 있고, OS 패키지는 계산 노드 이미지에도 있어야 합니다. GPU·RDMA 드라이버와 커널은 지원 조합을 확인합니다.

실행 중 노드가 RAM 기반이면 개별 설치는 재부팅 후 사라질 수 있습니다. 노드에 yum/dnf가 아예 없는 구성도 있으므로 “pdsh로 yum install”을 모든 환경에 적용하지 않습니다.

2. 버전·대상·복구 준비

OS·Warewulf·이미지·커널·서비스·저장소 버전과 적용 대상을 기록합니다. 현재 설정과 승인된 범위의 이전 이미지·구성을 보관하고 돌아갈 버전을 정합니다. 전체 OS 이미지나 사용자 데이터를 복사할 권한은 설정 보관 권한과 별도로 확인합니다.

3. Warewulf 3 + EL8 패키지 설치 형태

아래는 기존 이미지 디렉터리를 정확히 확인한 경우의 예입니다. CentOS 7의 yum 예제는 해당 레거시 환경에만 적용하며 OS8·9·10 저장소와 섞지 않습니다.

IMAGE=/YOUR_CONFIRMED_IMAGE_PATH
test -d "$IMAGE/etc"
cat "$IMAGE/etc/os-release"
dnf --installroot="$IMAGE" --releasever=8 install YOUR_APPROVED_PACKAGE
wwvnfs --chroot="$IMAGE"
wwsh vnfs list

각 명령 성공을 확인한 후 다음 단계로 진행합니다. 저장소·서명 확인·플랫폼·의존성·서비스 스크립트 오류를 해결하지 않은 채 강제 옵션으로 넘기지 않습니다. 관리 노드에도 필요한 패키지가 있으면 별도 설치합니다.

Warewulf 4는 image build/exec/shell과 overlay 방식이 다르므로 설치 버전의 wwctl 도움말과 공식 운영서를 사용합니다. 이 장의 wwvnfs를 대체 명령처럼 혼용하지 않습니다.

4. 실행 중 노드 반영

노드에 패키지 관리자가 있고 온라인 변경이 승인된 경우에만 같은 패키지 구성을 적용합니다. 대규모 동시 실행보다 한 노드부터 확인합니다. 이미지와 실행 중 노드의 상태가 달라지지 않도록 기록합니다.

온라인 설치가 불가능하거나 커널·서비스 변경이면 정상 재부팅으로 새 이미지를 적용합니다. 새 작업 차단 → 기존 직접·스케줄러 작업 확인 → 정상 종료·재부팅 → 검증 → 사용 재개 순서로 진행합니다. 일괄 강제 재부팅을 기본 예제로 사용하지 않습니다.

5. 배포 검증

rpm -q YOUR_APPROVED_PACKAGE
hostname
uname -r
findmnt -t nfs,nfs4
systemctl --failed

관리 노드·이미지의 패키지 목록과 노드의 실제 버전을 비교합니다. 프로그램은 일반 사용자로 단일 노드 → 필요한 멀티노드·IB → 라이선스 시험을 수행합니다. 재부팅 후에도 설치가 유지되는지 확인합니다.

6. 공용 응용프로그램과 Module

버전별 경로에 설치하고 기존 정상 버전을 유지합니다. Module로 새 버전을 선택하게 하며 전체 사용자의 기본값 변경은 검증 후 공지합니다. MPI·컴파일러·GPU 런타임을 함께 시험합니다. ANSYS 등 상용 제품은 설치 경로·라이선스·제공 MPI·Slurm 연동을 제품 담당자와 확정합니다.

7. 실패 시 복구

시험 노드를 사용 제외하고 실패 로그·버전·변경 내용을 보관합니다. 승인된 이전 이미지·overlay·패키지 구성으로 돌린 뒤 대표 노드를 먼저 검증합니다. 결과를 확인하기 전 다른 노드로 확대하지 않습니다. 변경과 복구 모두 사용자에게 영향 범위와 상태를 알립니다.

NFS 공유 저장소 추가

이 장의 목차
  • NFS 공유 저장소 추가
    • 1. 서버·클라이언트 현재 상태
    • 2. 공유 정책과 서버 반영
    • 3. 클라이언트 영구 마운트
    • 4. 이미지 재생성과 시험 노드
    • 5. 문제 해결

스토리지 연결·파일시스템 생성과 NFS 공유 추가는 다른 작업입니다. 이 장은 이미 준비되고 보존 범위가 확인된 파일시스템을 공유하는 절차이며 디스크 초기화 명령을 포함하지 않습니다.

1. 서버·클라이언트 현재 상태

findmnt
df -hT
cat /etc/exports
exportfs -v

대상 장치·UUID·마운트 경로·소유권·서비스 사용자·프로토콜·클라이언트 범위를 확인합니다. 데이터가 있는 마운트가 빠진 상태에서 빈 디렉터리를 공유하거나 그곳에 결과를 쓰지 않도록 주의합니다.

클라이언트에서는 findmnt -t nfs,nfs4, df -hT를 확인합니다. pdsh가 제공되면 승인된 노드 범위로 읽기 전용 조회를 먼저 수행합니다.

2. 공유 정책과 서버 반영

호스트·망 범위를 최소화하고 읽기/쓰기·root_squash·그룹 권한을 정합니다. 아래 주소는 문서 예시용이며 현장 값이 아닙니다.

/srv/projects 192.0.2.21(rw,sync,root_squash,no_subtree_check)

/etc/exports.d 사용 가능 여부를 확인하고 전용 .exports 파일로 관리하거나 기존 exports를 승인된 방식으로 수정합니다. 무조건 echo >>를 반복해 중복 행을 만들지 않습니다. 변경 전 파일 사본을 보관합니다.

exportfs -ra
exportfs -v

서버·방화벽에서 실제 NFS 버전의 요구 사항을 확인합니다. 전체 서버 재시작이 필요한지 판단하고 활성 작업의 영향을 검토합니다. 클라이언트 root 쓰기 실패만으로 no_root_squash를 적용하지 않습니다.

3. 클라이언트 영구 마운트

새 마운트 지점을 이미지·overlay·구성 관리에 생성하고 fstab 등의 영구 설정을 반영합니다. 예제의 서버명과 경로를 실제 값으로 바꾸고 사용하는 NFS 버전을 검증합니다.

YOUR_NFS_SERVER:/srv/projects /projects nfs vers=4.1,_netdev 0 0

실제 필요에 따라 ro/rw·nodev·nosuid 등 옵션을 정합니다. 배포 도구가 fstab을 생성한다면 수동 수정이 덮어써지지 않도록 생성 원본을 수정합니다. 임의의 작은 rsize/wsize를 과거 문서에서 그대로 가져오지 않습니다.

4. 이미지 재생성과 시험 노드

Warewulf 3이면 승인된 이미지 변경 후 wwvnfs --chroot=YOUR_IMAGE_PATH를 실행하고 성공을 확인합니다. Warewulf 4는 이미지·overlay 빌드를 버전에 맞게 수행합니다.

작업을 비운 시험 노드에서 적용하고 다음을 확인합니다.

findmnt /projects
df -hT /projects
ls -ld /projects

일반 사용자로 승인된 하위 폴더에서 생성·읽기·삭제·그룹 공유·소유권을 검증합니다. 모든 노드가 같은 저장소를 보는지와 재부팅 후 마운트도 확인한 뒤 확대 적용합니다.

5. 문제 해결

증상 확인
접근 거부 exports의 대상 주소, 서버·클라이언트 이름 해석, 방화벽
root만 쓰기 실패 root_squash 정책과 사용자로 수행할 작업인지
사용자 파일 소유권이 숫자로 보임 UID/GID·인증·NFS idmapping
명령이 오래 멈춤 서버 저장소·네트워크·NFS 응답. 활성 마운트 강제 해제 전 작업 영향 확인
재부팅 후 마운트 누락 이미지/overlay/fstab 원본과 부팅 의존성

저장소 용량·inode·quota·백업 상태도 별개로 확인합니다. 공유 변경이 데이터 백업을 대신하지 않습니다.

공유 Python 설치와 Module 제공

이 장의 목차
  • 공유 Python 설치와 Module 제공
    • 1. 버전·경로·빌드 환경
    • 2. 빌드 의존성
    • 3. 소스 검증·빌드·설치
    • 4. Lua Module 파일
    • 5. 일반 사용자·노드 검증

기존 시스템 Python을 교체하지 않고 버전별 공유 설치본을 제공하는 절차입니다. OS 관리 도구가 사용하는 Python과 연구용 Python을 분리합니다. Conda로 제공할지 소스 빌드할지 먼저 결정합니다.

1. 버전·경로·빌드 환경

지원 중인 Python 릴리스, 사용하는 OS·OpenSSL·컴파일러와 대상 노드의 CPU 범위를 확인합니다. 오래된 Python 3.5 예제는 현재 기본 설치 기준으로 사용하지 않습니다. 아래의 버전·경로 자리표시는 승인된 값으로 바꿉니다.

PYVER=YOUR_APPROVED_PYTHON_VERSION
PREFIX=/YOUR_SHARED_SOFTWARE_ROOT/python/$PYVER

빌드는 부하를 허용한 관리·빌드 서버에서 수행합니다. 특정 CPU의 -march=native로 만든 바이너리가 다른 세대 노드에서 실패하지 않는지 확인합니다. 설치 경로는 기존 버전과 분리합니다.

2. 빌드 의존성

Enterprise Linux 계열의 패키지 형태입니다. 저장소와 Python 버전에 따라 추가 의존성이 필요할 수 있습니다.

dnf install gcc make zlib-devel bzip2-devel xz-devel \
  readline-devel sqlite-devel openssl-devel libffi-devel

Ubuntu·SUSE 등 다른 배포판에는 해당 배포판의 개발 패키지 이름을 사용합니다. OpenSSL·시스템 라이브러리를 전체 노드에서 임의로 교체하지 않습니다.

3. 소스 검증·빌드·설치

mkdir -p "$HOME/python-build"
cd "$HOME/python-build"
curl -fLO "https://www.python.org/ftp/python/$PYVER/Python-$PYVER.tgz"
sha256sum "Python-$PYVER.tgz"

Python 공식 배포의 체크섬·검증 절차와 비교한 후 압축을 풉니다.

tar -xzf "Python-$PYVER.tgz"
cd "Python-$PYVER"
./configure --prefix="$PREFIX" --with-ensurepip=install --enable-shared
make -j2
make test
make altinstall

각 단계의 성공을 확인하고 테스트가 실패하면 원인을 검토합니다. 실제 설치 권한은 prefix에만 필요한 범위로 사용합니다. 공유 라이브러리를 사용하면 시험 실행에도 해당 lib 경로가 필요할 수 있습니다. altinstall의 버전 있는 실행파일 이름을 확인하고 시스템 /usr/bin/python* 링크를 바꾸지 않습니다.

4. Lua Module 파일

Lmod가 제공되는 경우의 파일 형태입니다. 실제 설치 경로·버전을 입력해 현장의 모듈 트리에 python/YOUR_VERSION.lua로 저장합니다.

help([[Shared research Python. Use the versioned executable or a project venv.]])
whatis("Name: Python")
whatis("Version: YOUR_VERSION")
conflict("python")
local root = "/YOUR_SHARED_SOFTWARE_ROOT/python/YOUR_VERSION"
prepend_path("PATH", pathJoin(root, "bin"))
prepend_path("LD_LIBRARY_PATH", pathJoin(root, "lib"))

현장이 Tcl 기반 Environment Modules를 사용하면 맞는 형식으로 작성합니다. 모듈 파일은 사용자에게 읽혀야 하며 관리자가 수정합니다. 모듈 캐시는 현장의 Lmod 버전과 정책에 따라 갱신하고 다른 사용자의 캐시를 일괄 삭제하지 않습니다.

5. 일반 사용자·노드 검증

module avail
module show python/YOUR_VERSION
module load python/YOUR_VERSION
command -v YOUR_VERSIONED_PYTHON
YOUR_VERSIONED_PYTHON --version
YOUR_VERSIONED_PYTHON -c 'import ssl, sqlite3, bz2, lzma, ctypes; print(ssl.OPENSSL_VERSION)'
YOUR_VERSIONED_PYTHON -m pip --version

설치된 실제 실행파일 이름으로 바꿉니다. 일반 사용자로 여러 노드에서 같은 버전·동적 라이브러리 로드·패키지 import를 확인합니다. 시스템 Python과 개인 Conda 환경이 바뀌지 않았는지도 확인합니다.

개인 패키지는 프로젝트 venv 또는 Conda 환경에 설치하게 합니다. 공용 Python에 모든 사용자의 패키지를 즉흥적으로 추가하지 않습니다. 공용 패키지 변경은 버전·환경 파일·시험 결과를 기록하고 이전 정상 버전을 유지합니다.

계산 노드 추가·교체·정보 변경

이 장의 목차
  • 계산 노드 추가·교체·정보 변경
    • 1. 신규·교체 노드 확인표
    • 2. Warewulf 3 등록 형태
    • 3. DHCP·PXE 반영
    • 4. 부팅 검증
    • 5. 스케줄러와 자원 등록

1. 신규·교체 노드 확인표

노드명, 관리 NIC MAC·포트, 관리 IP, 고속망 IP·장치, BMC, CPU·메모리·GPU, UEFI/Legacy·Secure Boot, 부팅 이미지·커널, 로컬 디스크 보존 범위를 확인합니다. MAC과 IP 중복은 기존 노드 통신·DHCP에 영향을 줄 수 있습니다.

교체 시 기존 노드의 직접 작업·예약·스케줄러 상태를 확인하고 사용 제외합니다. 등록 정보 변경과 로컬 디스크 초기화는 별도 작업입니다. 새 노드 등록만으로 디스크 포맷을 승인한 것으로 보지 않습니다.

2. Warewulf 3 등록 형태

배포 대상 버전과 옵션은 wwsh 도움말에서 확인합니다. 아래는 기존 이미지·bootstrap을 재사용하는 형태입니다.

wwsh node list
wwsh vnfs list
wwsh bootstrap list
wwsh file list
wwsh node new YOUR_NODE --netdev YOUR_MGMT_NIC \
  --ipaddr=YOUR_MGMT_IP --hwaddr=YOUR_MGMT_MAC \
  --netmask=YOUR_MGMT_NETMASK --gateway=YOUR_MGMT_GATEWAY
wwsh provision set YOUR_NODE --vnfs=YOUR_VNFS \
  --bootstrap=YOUR_BOOTSTRAP --files=YOUR_APPROVED_FILE_LIST
wwsh node print YOUR_NODE
wwsh provision print YOUR_NODE

배포 파일 목록에는 실제 인증·네트워크 구성에 필요한 승인 파일만 지정합니다. 과거 예제의 shadow 포함 목록을 그대로 복사하지 않습니다. IB 등 추가 인터페이스는 별도 등록·템플릿 설정으로 반영하고 관리망과 혼동하지 않습니다.

기존 노드의 NIC 교체·IP 변경은 신규 중복 객체를 만들지 말고 해당 버전의 node set 등 변경 명령을 확인합니다. 수정 전 기존 값을 보관하고 대상 한 대를 다시 조회합니다.

3. DHCP·PXE 반영

등록 정보를 확인한 뒤 현장의 PXE 설정을 생성합니다.

wwsh pxe update

DHCP 구성 검증·갱신·서비스 reload/restart는 사용하는 DHCP 서버의 실제 설정에 따라 수행합니다. 관리망 인터페이스와 서비스 범위를 확인하고 외부망에 새 DHCP 서비스를 잘못 제공하지 않습니다. 여러 노드 등록 중 반복 재시작으로 서비스가 실패 상태가 되지 않는지도 확인합니다.

Warewulf 4는 wwctl의 이미지·노드·프로파일·overlay 절차로 수행합니다. 버전 3 명령을 그대로 적용하지 않습니다.

4. 부팅 검증

  1. PXE할 NIC·UEFI/Legacy·Secure Boot 정책을 확인합니다.
  2. 승인된 정상 기동 또는 1회 부팅 설정으로 대표 노드를 부팅합니다.
  3. DHCP → bootloader → 커널/initramfs → 이미지 전송 → 초기화 순서의 로그를 확인합니다.
  4. SSH·계정·IP·IB·시간 동기화·공유 마운트·서비스를 확인합니다.
  5. 일반 사용자 계산·멀티노드·필요한 라이선스 시험을 합니다.
  6. 재부팅해 영구 부팅 경로와 구성이 유지되는지 확인합니다.

전원 On이나 DHCP 응답만으로 OS 부팅 완료로 표시하지 않습니다. 하드웨어 POST가 길거나 멈춘 경우 BMC 콘솔·이벤트 시각을 함께 확인합니다.

5. 스케줄러와 자원 등록

Slurm 사용 시 노드의 slurmd -C 등으로 실제 CPU 토폴로지·메모리를 확인하고 OS·RAM 루트 여유를 고려해 설정합니다. 새 노드명·NodeAddr·Partition·GRES·인증·회계 필요 사항을 반영하고 시험 작업으로 등록을 검증합니다. 기존 노드와 CPU 세대·GPU·메모리가 다르면 Feature·Partition 등 정책을 검토합니다.

사용자 안내·모니터링·하드웨어 대응표·예약 체계도 갱신합니다. 교체한 노드의 예전 키·인증 정보는 현장 절차로 회수합니다.

마스터 호스트명·IP 변경

이 장의 목차
  • 마스터 호스트명·IP 변경
    • 1. 변경 범위와 복구 경로
    • 2. 영향 목록
    • 3. 현재 구성 조사
    • 4. 적용 순서
    • 5. 검증과 복구 기준

원격 접속 단절과 전체 노드 부팅·공유 저장소·인증에 영향을 줄 수 있는 작업입니다. 실제 운영망별 변경 계획과 복구 접속 수단을 준비한 후 수행합니다. 이 장은 전체 설정을 일괄 치환하는 스크립트가 아닙니다.

1. 변경 범위와 복구 경로

외부 접속 IP, 관리망 IP, IB IP, 호스트명·DNS 중 무엇을 바꾸는지 구분합니다. 담당자·점검 시간·주소 할당·DNS·방화벽·중계 서버·허용 목록·복구 콘솔을 확인하고 이전 값을 기록합니다. 현재 작업의 정상 종료 또는 유지 가능 여부를 판단합니다.

외부 접속 세션 하나만을 유일한 복구 수단으로 두지 않습니다. BMC·직접 콘솔·승인된 관리 경로를 확인합니다. 네트워크 변경만으로 해결되지 않는 라이선스의 host ID·호스트명 종속성도 제품 담당자에게 확인합니다.

3. 현재 구성 조사

hostnamectl
ip -br addr
ip route
nmcli connection show
findmnt -t nfs,nfs4

NetworkManager를 사용하지 않는 OS 구성에서는 해당 관리 도구를 확인합니다. 이전 이름을 검색할 때도 경로·검색어를 제한하고 출력에 비밀정보가 포함되지 않는지 확인합니다. /etc 전체를 일괄 sed 치환하지 않습니다.

4. 적용 순서

  1. 설정 보관·복구 수단·서비스 의존 관계와 작업 상태를 확인합니다.
  2. 주소 중복·게이트웨이·DNS·라우팅·방화벽 변경을 준비합니다.
  3. 관리 도구에서 승인된 연결·호스트명 변경을 적용합니다.
  4. 새 세션으로 외부·관리망·필요한 IB 경로를 확인합니다.
  5. DHCP·PXE·NFS·시간·스케줄러·라이선스 등 관련 설정을 수정합니다.
  6. 이미지·overlay·배포 파일을 갱신하고 대표 노드를 시험합니다.
  7. 사용자 안내·모니터링을 갱신하고 전체 대상 적용을 완료합니다.

5. 검증과 복구 기준

새 접속, DNS, 노드 부팅, 사용자 인증, 공유 경로, 라이선스, 실제 계산을 확인합니다. 재부팅 후 연결 프로필과 서버 참조가 유지되는지 검증합니다. 예정 시간 내 복구 조건을 충족하지 못하면 준비한 이전 주소·프로필·서비스 설정으로 되돌리고 영향 범위를 확인합니다.

전원 조작은 승인된 관리자만 수행합니다. 먼저 대상 노드와 BMC의 대응표를 확인하고 사용자 작업·저장소 쓰기·점검 시간을 검토합니다. 조회 → 정상 종료 → 전원 상태 확인 순서를 기본으로 합니다.

1. IPMI 상태 조회

ipmitool이 제공되고 승인된 BMC 관리망에서 접근하는 경우입니다. -a는 암호 입력을 요청하며 비밀번호를 명령 인수에 넣지 않습니다.

ipmitool -I lanplus -H YOUR_BMC_HOST -U YOUR_BMC_USER -a chassis power status
ipmitool -I lanplus -H YOUR_BMC_HOST -U YOUR_BMC_USER -a chassis status
ipmitool -I lanplus -H YOUR_BMC_HOST -U YOUR_BMC_USER -a sel elist last 10

전원 상태·하드웨어 오류·이벤트 시각을 확인합니다. IPMI망은 일반 사용자에게 공개하지 않습니다.

2. 정상 종료와 전원 켜기

OS에 접속 가능하면 해당 OS의 정상 종료 절차를 우선합니다. 승인된 대상 한 대에서 수행하는 예입니다.

ssh YOUR_ADMIN_USER@YOUR_CONFIRMED_NODE 'sudo systemctl poweroff'

OS가 ACPI 종료를 지원하는 경우 IPMI의 soft 요청을 사용할 수 있습니다.

ipmitool -I lanplus -H YOUR_BMC_HOST -U YOUR_BMC_USER -a chassis power soft
ipmitool -I lanplus -H YOUR_BMC_HOST -U YOUR_BMC_USER -a chassis power status

종료 완료와 전원 Off를 확인한 뒤 필요한 경우 켭니다.

ipmitool -I lanplus -H YOUR_BMC_HOST -U YOUR_BMC_USER -a chassis power on

off, reset, cycle은 정상 종료와 같지 않습니다. OS 불응 시의 장애 대응 절차에서 데이터 손상 위험과 승인을 확인한 후 사용합니다. 반복 전원 사이클을 원인 조사 대신 수행하지 않습니다.

3. PXE 부팅 대상 확인

ipmitool -I lanplus -H YOUR_BMC_HOST -U YOUR_BMC_USER -a chassis bootparam get 5

부팅 장치 변경은 UEFI/Legacy, 1회/영구 적용, PXE할 NIC와 로컬 디스크 보존 범위를 확인합니다. 명령이 성공해도 BMC가 실제 어떤 플래그를 저장했는지 다시 조회합니다. 모든 장비에 같은 raw 명령이나 부팅 옵션을 적용하지 않습니다.

4. Dell RACADM

해당 iDRAC 버전에서 지원되는 명령을 확인합니다. SSH 호스트 지문을 검증한 뒤 BMC에 로그인하는 방법은 비밀번호를 명령 인수에 넣는 원격 RACADM보다 노출을 줄일 수 있습니다.

ssh YOUR_BMC_USER@YOUR_BMC_HOST

BMC SSH 콘솔에서 지원되는 경우:

racadm serveraction powerstatus
racadm serveraction graceshutdown
racadm serveraction powerup

powerdown·powercycle·hardreset 등은 정상 종료와 다를 수 있으므로 장비 문서와 장애 절차를 확인합니다. chassis 관리 장비는 추가 대상 지정 형식이 다를 수 있습니다.

5. Wake-on-LAN

NIC·BIOS·전원·스위치·네트워크에서 WOL을 지원하고 활성화한 경우에만 사용합니다. 부팅용 OS NIC의 승인된 MAC을 확인하며 BMC MAC과 혼동하지 않습니다.

wakeonlan YOUR_CONFIRMED_NIC_MAC

브로드캐스트·라우팅과 전원 상태에 따라 도달하지 않을 수 있습니다. 명령을 보냈다는 것만으로 기동 성공을 판단하지 말고 BMC·OS 부팅·서비스를 확인합니다.

6. 여러 노드 조작

pdsh 등의 도구가 있더라도 먼저 대상 범위의 hostname 같은 읽기 전용 명령으로 대응을 검증합니다. 작업 현황·정상 종료·동시 기동 전력·부팅 서버 부하를 검토하고 작은 묶음으로 적용합니다. 무조건 모든 노드에 강제 종료를 전달하는 예제는 사용하지 않습니다.
