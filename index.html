내 PC에서 실행

Windows는 PowerShell/OpenSSH 또는 조직에서 허용한 SSH 클라이언트를, macOS·Linux는 터미널을 사용할 수 있습니다. 클라이언트별 기능·라이선스는 해당 배포처에서 확인합니다.

ssh -p YOUR_SSH_PORT YOUR_USER@YOUR_LOGIN_HOST

처음 접속할 때 표시되는 호스트 키 지문은 관리자에게 받은 지문과 비교합니다. 호스트 키가 변경되었다는 경고가 나오면 재설치·교체 여부를 확인합니다. 경고를 우회하거나 기존 키를 무조건 삭제하지 않습니다.

비밀번호 입력 중 화면에 글자가 보이지 않는 것은 정상입니다. 비밀번호·다중 인증·키 인증 중 현장에서 지정한 방법을 사용합니다.

중계 서버·VPN이 필요한 현장에서는 관리자에게 받은 전용 접속 절차를 사용합니다. 중계 서버의 127.0.0.1과 내 PC의 127.0.0.1은 다른 대상입니다. 리버스 유지보수 통로를 일반 사용자 접속 경로로 임의 사용하지 않습니다.

운영체제별 접속 준비

Windows: MobaXterm 또는 OpenSSH

MobaXterm을 사용하는 경우 Session → SSH에서 Remote host, Specify username, Port를 입력합니다. 터미널의 SSH 명령으로도 접속할 수 있습니다. SFTP 패널은 세션·인증 설정에 따라 제공되며 패널에서 파일을 올리기 전에 대상 폴더를 확인합니다. 조직 정책과 해당 에디션의 사용 조건을 확인합니다.

PowerShell의 OpenSSH는 ssh -V로 설치 여부를 확인할 수 있습니다. GUI 화면 전달이 필요하면 별도 X 서버가 필요하며, MobaXterm에서는 내장 X 서버 기능을 사용할 수 있습니다.

Windows 사용자명·경로에 한글이 있어 클라이언트 오류가 발생하면 오류 메시지와 버전을 확인하고 지원되는 최신 버전·작업 경로 설정을 담당자에게 문의합니다. 기존 .bashrc를 덮어쓰거나 시스템 ssh_config를 무조건 치환하지 않습니다.

macOS: Terminal과 선택적 XQuartz

터미널의 SSH로 접속할 수 있습니다. 텍스트 접속에는 XQuartz가 필요하지 않습니다. X11 GUI를 사용하는 경우 XQuartz를 설치·실행하고 새 터미널에서 ssh -X를 사용합니다. 필요 시 로그아웃 후 다시 로그인하는 등 설치 안내를 따릅니다.

Linux: Terminal

SSH 클라이언트가 있는지 ssh -V로 확인합니다. X11 전달에는 로컬 X 서버와 서버의 전달 허용·인증 도구 등이 필요합니다. headless 환경에서 별도 준비 없이 GUI가 열린다고 가정하지 않습니다.

GUI 접속과 터널

ssh -X -p YOUR_SSH_PORT YOUR_USER@YOUR_LOGIN_HOST

-X는 X11 전달, -C는 압축, -Y는 신뢰하는 X11 전달 옵션입니다. 일반 접속에 모두 필요하지는 않습니다. 신뢰하는 서버에서 제품이 요구할 때만 관리자에게 -Y 사용을 확인합니다. GUI가 안 열리면 echo "$DISPLAY"와 X 서버·전달 설정을 확인하고 GUI 안내를 참고합니다.

승인된 중계 서버를 거치는 ProxyJump 형태는 다음과 같습니다. 중계 SSH 포트와 최종 SSH 포트는 별개입니다.

ssh -J YOUR_JUMP_USER@YOUR_JUMP_HOST:YOUR_JUMP_PORT \
  -p YOUR_TARGET_PORT YOUR_USER@YOUR_TARGET_HOST

리버스 터널 유지보수 포트를 사용하는 현장은 별도 안내를 받습니다. 접속 편의를 위해 에이전트 전달이나 호스트 키 검사를 일괄 해제하지 않습니다.

접속한 서버에서 확인

hostname
whoami
pwd

현장 안내서의 로그인 노드 이름과 개인 계정이 표시되는지 확인합니다. 계산 노드 접속이 별도로 필요한 경우에만 승인된 방식으로 이동합니다.

추가로 w, uptime, free -h, df -h .로 상황을 확인할 수 있습니다. nvidia-smi는 GPU와 드라이버가 제공된 노드에서 사용합니다. 이 명령들이 사용 예약을 대신하지는 않습니다.

자주 접속하는 서버 저장

개인 PC의 ~/.ssh/config에 별칭을 등록할 수 있습니다. Windows OpenSSH는 보통 사용자 프로필의 .ssh/config를 사용합니다.

Host research-cluster
    HostName YOUR_LOGIN_HOST
    User YOUR_USER
    Port YOUR_SSH_PORT
    ServerAliveInterval 30
    ServerAliveCountMax 3

실제 값으로 바꾼 후 ssh research-cluster로 접속합니다. 설정 파일에는 비밀번호를 넣지 않습니다. 연결 확인 옵션은 죽은 연결 감지에 도움이 되지만 실행 작업을 자동 복구하지는 않습니다.

파일 주고받기

    • SFTP에서 파일 전송
    • rsync로 반복·대용량 전송

다음 예제는 HOME이 작업에 허용된 공유 경로일 때만 사용합니다. 별도 프로젝트 경로가 있으면 그 경로에서 시작합니다.

mkdir -p "$HOME/work/first-test"
cd "$HOME/work/first-test"
pwd
df -h .

내 PC에서 작은 파일을 올리는 예제입니다. YOUR_USER_HOME은 /home/개인계정 등 관리자가 안내한 절대 경로로 바꿉니다.

scp -P YOUR_SSH_PORT ./input.dat YOUR_USER@YOUR_LOGIN_HOST:YOUR_USER_HOME/work/first-test/

결과를 내 PC의 현재 폴더로 내려받습니다.

scp -P YOUR_SSH_PORT YOUR_USER@YOUR_LOGIN_HOST:YOUR_USER_HOME/work/first-test/result.dat ./

SSH는 소문자 -p, SCP는 대문자 -P로 포트를 지정합니다. GUI 파일 전송에서는 SFTP를 선택하고 같은 주소·계정·SSH 포트를 사용합니다. 중계 접속이면 별도 SFTP 중계 설정이 필요할 수 있습니다.

대용량·다수 파일은 양쪽에 rsync가 제공될 때 사용할 수 있습니다. 재실행 시 이미 전송된 내용을 활용하며 --partial은 중단된 부분 파일을 보관합니다. 대상 경로와 덮어쓰기 여부를 먼저 확인합니다.

rsync -av --partial --progress -e 'ssh -p YOUR_SSH_PORT' ./inputs/ YOUR_USER@YOUR_LOGIN_HOST:YOUR_USER_HOME/work/first-test/inputs/

이 예제에는 파일 삭제 옵션을 넣지 않았습니다. 중요한 결과는 현장 백업·보관 정책에 따라 별도 보존합니다.

폴더 전체 전송

SCP는 -r로 폴더를 전송합니다. 현재 PC에서 실행하는 예입니다.

scp -r -P YOUR_SSH_PORT ./inputs YOUR_USER@YOUR_LOGIN_HOST:YOUR_USER_HOME/work/first-test/

서버 간 직접 전송은 양쪽 인증과 통신 경로가 필요합니다. 어떤 장비를 경유하는지는 SCP 버전·옵션에 따라 달라지므로 승인된 전송 방법을 확인합니다. 비밀키를 임시로 여러 서버에 복사하지 않습니다.

SFTP에서 파일 전송

sftp -P YOUR_SSH_PORT YOUR_USER@YOUR_LOGIN_HOST

접속 후 pwd·ls는 원격 경로를, lpwd·lls는 내 PC 경로를 확인합니다. cd·lcd로 각각 이동하고 put input.dat, get result.dat로 전송합니다. 종료는 bye입니다. GUI에서는 서버·포트·계정·인증 방식을 동일하게 지정합니다.

rsync로 반복·대용량 전송

source/는 폴더 안의 내용, source는 폴더 자체를 복사하는 차이가 있습니다. 전송 전 경로를 미리 확인합니다.

rsync -av --dry-run -e 'ssh -p YOUR_SSH_PORT' ./inputs/ \
  YOUR_USER@YOUR_LOGIN_HOST:YOUR_USER_HOME/work/first-test/inputs/

출력을 확인한 후 --dry-run을 빼고 --partial --progress를 추가해 전송합니다. 이미 압축된 데이터는 -z 압축이 도움이 되지 않을 수 있습니다. rsync의 재실행은 이미 같은 파일을 건너뛰거나 차이를 활용할 수 있으나, 모든 프로그램·모든 파일 형식에서 무조건 이어받기를 보장하는 표현으로 이해하지 않습니다.

--delete는 대상의 파일을 제거할 수 있으므로 일상 복사 예제에는 사용하지 않습니다. 입력·결과 경로를 뒤집거나 공유 폴더 루트를 대상으로 잡지 않습니다.

전송 결과 검증과 권한

ls -lh input.dat
sha256sum input.dat

중요 파일은 전송 전후 체크섬을 비교합니다. 파일 개수·크기뿐 아니라 프로그램에서 읽히는지도 확인합니다. Permission denied는 파일·상위 폴더 권한과 대상 계정을, 용량 오류는 df·quota를 확인합니다. 권한을 일괄 777로 바꾸지 않습니다. 대규모 작은 파일은 저장소 부하를 고려해 담당자와 묶음 전송 방식을 협의합니다.

직접 실행

이 절차는 스케줄러를 통하지 않는 실행이 허용되고 노드 직접 접속 권한이 제공된 경우에만 적용합니다. ANSYS 등 제품 자체의 원격 실행 도구를 사용하는 현장은 제품별 안내를 우선합니다.

실행 전

관리자 또는 예약 체계에서 사용할 노드·CPU·메모리·종료 시각을 확인합니다. 아래 명령은 상황을 보는 보조 수단이며 예약이나 자원 점유권을 보장하지 않습니다.

ssh YOUR_APPROVED_NODE
hostname
uptime
free -h
ps -u "$USER" -o pid,etime,%cpu,%mem,args

w는 로그인 세션을 보여줄 뿐, 모든 계산 작업을 보여주지는 않습니다. 다른 사람이 로그인하지 않았어도 계산 중일 수 있습니다. GPU 확인 명령은 해당 GPU와 도구가 설치된 노드에서만 사용합니다.

계산 시작

지정한 공유 작업 폴더에서 제품별 안내 명령으로 실행합니다. 다음은 문법 설명용이며 실제 실행 명령이 아닙니다.

YOUR_APPLICATION YOUR_CONFIRMED_OPTIONS > run.log 2>&1

코어 수·MPI 방식·노드 목록·메모리 옵션은 프로그램별로 다릅니다. 단일 노드 계산 성공 후 멀티노드 계산을 시험합니다. 여러 노드에서 같은 파일을 동시에 덮어쓰지 않도록 작업 폴더와 출력 파일을 분리합니다.

ANSYS의 경우 제품·버전·실행 경로·라이선스 서버·HPC 사용 권한·MPI/IB 설정을 설치 담당자에게 확인합니다. 클러스터의 일반 OpenMPI 모듈을 ANSYS용 MPI로 자동 지정하지 않습니다.

접속 종료 후에도 유지해야 하는 작업

현장에서 tmux 사용을 허용하고 설치한 경우의 예입니다. 프로그램을 실행할 계산 노드에서 시작합니다.

tmux new -s first-test

세션 안에서 계산을 시작합니다. Ctrl+b를 누른 뒤 d를 누르면 세션에서 분리됩니다. 같은 노드·같은 계정으로 돌아와 다시 연결합니다.

tmux attach -t first-test

tmux는 노드 재부팅·장애를 견디는 작업 관리자가 아니며, 현장의 로그아웃 정리 정책에 따라 유지되지 않을 수 있습니다. 긴 계산에는 프로그램의 체크포인트 기능과 승인된 실행 방식을 확인합니다.

진행 확인과 중지

다른 접속 세션에서도 작업이 실행되는 같은 노드·같은 경로에서 확인합니다.

tail -n 50 run.log
tail -f run.log

tail -f는 Ctrl+c로 종료해도 계산이 중단되지 않습니다. 계산 자체는 제품의 정상 종료·체크포인트 저장 기능을 먼저 사용합니다. 프로세스를 종료해야 하면 본인 PID와 작업을 확인한 뒤 kill -TERM PID를 사용합니다. MPI 작업은 여러 프로세스를 만들 수 있으므로 실행기 또는 제품이 안내한 종료 방법을 따릅니다. killall, 다른 사용자의 PID, 강제 종료를 일반 절차로 사용하지 않습니다.

Slurm으로 작업 제출

아래는 첫 작업용 요약입니다. CPU·메모리·GPU 요청, Conda·컨테이너 배치 작업, MPI, 우선순위·시작 예상시간은 Slurm 상세 사용을 확인하세요. Slurm을 사용하지 않는 현장은 이 절을 건너뜁니다. 파티션·제한 정책은 현장 안내서에 따릅니다.

sinfo
squeue -u "$USER"

첫 배치 작업은 계산하지 않는 작은 시험으로 시작합니다. 로그인 노드의 공유 작업 폴더에서 다음 파일을 만듭니다.

cat > hello.slurm <<'EOF'
#!/bin/bash
#SBATCH --job-name=hello
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1
#SBATCH --time=00:02:00
#SBATCH --output=hello-%j.out
hostname
date
EOF
sbatch -p YOUR_PARTITION hello.slurm

제출 응답의 Job ID를 기록하고 squeue -u "$USER"로 확인합니다. 완료 후 현재 폴더의 hello-작업번호.out을 확인합니다. 취소는 scancel YOUR_JOB_ID를 사용합니다.

srun hostname 같은 명령은 실행할 명령이 끝나면 종료됩니다. srun --pty bash로 대화형 셸을 시작한 경우 셸을 exit로 끝내야 합니다. 작업 목록에서 사라졌다는 것만으로 계산 성공을 판단하지 말고 출력·오류 로그와 결과를 확인합니다. sacct는 회계 기능이 구성된 경우에 사용합니다.

1. 사용 가능 여부와 설치

이미 제공되는 Conda 모듈·설치본이 있는지 먼저 확인합니다. 없다면 담당자가 승인한 배포판·채널과 현재 라이선스 조건을 확인합니다. Anaconda Distribution과 Miniconda 등은 구성·배포 조건이 다릅니다.

command -v conda
conda --version
conda env list

직접 설치가 허용된 경우 공식 배포 안내에서 CPU 아키텍처에 맞는 설치 스크립트와 체크섬을 확인합니다. 서버에 브라우저가 없으면 내 PC에서 링크를 확인해 내려받거나 파일을 전송합니다.

cd "$HOME"
curl -fL 'YOUR_APPROVED_INSTALLER_URL' -o conda-installer.sh
sha256sum conda-installer.sh
bash conda-installer.sh

체크섬을 배포처의 값과 비교한 후 설치합니다. 관리자 승인 없이 root로 실행하지 않습니다. 초기화가 필요한 셸은 설치 안내에 따라 conda init bash를 적용하고 새 셸을 엽니다. 기존 .bashrc를 통째로 덮어쓰지 않습니다.

conda config --set auto_activate_base false
conda info

Conda 자체 업데이트는 관리되는 공유 설치본인지 먼저 확인합니다. 개인 설치본에서 승인된 경우 conda update -n base conda를 사용하되, 작업 도중 환경을 바꾸지 않습니다.

2. 환경 생성·활성화·종료

Python 버전은 응용프로그램 지원 조건에 맞춰 선택합니다. 아래 3.11은 예시이며 모든 제품의 요구 버전은 아닙니다.

conda create -n research-demo python=3.11 pip
conda activate research-demo
command -v python
python --version
python -m pip --version
python -m pip install numpy
python -c 'import numpy; print(numpy.__version__)'
conda deactivate

환경 안에서 python -m pip를 쓰면 대상 Python을 분명히 할 수 있습니다. 시스템 Python에 패키지를 설치하지 않습니다. 여러 노드에서 공유 환경을 동시에 변경하지 않습니다.

3. TensorFlow와 CUDA 환경

GPU 드라이버, Python, TensorFlow, CUDA 런타임의 호환 조합을 먼저 확인합니다. 오래된 TensorFlow 1.x·Python 3.6·CUDA 9 예제는 레거시 조합이며 현재 장비용 기본 설치 명령이 아닙니다. 기존 연구의 재현이 필요하면 격리된 환경·컨테이너와 원래 요구사항을 담당자에게 확인합니다.

현재 Linux용 TensorFlow가 지원하는 조건을 만족하고 해당 GPU 자원 사용이 승인된 경우의 설치 형태입니다. 버전을 생략해 자동으로 바뀌게 두기보다 프로젝트에서 검증한 값을 지정합니다.

conda activate research-demo
python -m pip install 'tensorflow[and-cuda]==YOUR_SUPPORTED_TF_VERSION'
python -c 'import tensorflow as tf; print(tf.__version__); print(tf.config.list_physical_devices("GPU"))'

CPU용 설치는 지원 버전의 tensorflow 패키지를 사용합니다. 다른 버전의 시스템 CUDA·Module·pip 런타임을 무조건 함께 올리지 않습니다. TensorFlow 설치 문서를 기준으로 OS·GPU·드라이버를 확인합니다.

4. 스크립트와 배치 실행

일괄 실행에서는 .bashrc에만 의존하지 말고 Conda 설치 경로를 명시합니다. YOUR_CONDA_ROOT를 실제 경로로 바꿉니다.

cat > run-python.sh <<'EOF'
#!/bin/bash
set -euo pipefail
source YOUR_CONDA_ROOT/etc/profile.d/conda.sh
conda activate research-demo
python -u ./your_program.py > python-run.log 2>&1
EOF
bash -n run-python.sh
bash run-python.sh

계산 노드와 자원을 배정받은 후 실행합니다. 단일 명령에는 conda run -n research-demo python your_program.py도 사용할 수 있습니다. Slurm 예제는 작업 제출 안내를 확인합니다.

전체 YAML은 설치된 의존성까지, history는 직접 요청한 항목 중심으로 기록합니다. explicit 목록은 같은 플랫폼의 재현에 적합합니다. 채널·플랫폼·pip 의존성·빌드가 달라지면 동일 결과가 보장되지 않습니다. 내보낸 파일의 개인 경로·사설 채널 인증정보를 확인한 뒤 공유합니다.

사용하지 않는 환경은 실행 중인 작업이 없는지 확인한 후 제거합니다.

conda deactivate
conda env remove -n research-rebuild
conda env list

로그인 때 특정 환경을 자동 활성화할 수 있으나, 다른 프로그램·MPI와 충돌할 수 있습니다. 기본 자동 활성화보다는 실행 스크립트에서 환경을 지정하는 방법을 권합니다. 자동화가 필요하면 .bashrc의 기존 Conda 초기화 부분을 보존하고 사용자 추가 부분만 수정합니다.

1. 기본 명령

Module은 관리자 설치본의 PATH·라이브러리 경로 등을 세션에 반영합니다. 프로그램 자체를 새로 설치하는 명령이 아닙니다. Lmod와 Environment Modules의 기능은 일부 다르므로 제공되는 도구를 확인합니다.

type module
module --version
module list
module avail
module show YOUR_MODULE
module load YOUR_MODULE
module unload YOUR_MODULE

Lmod에서 ml은 짧은 명령으로 사용할 수 있습니다. module spider YOUR_KEYWORD는 계층형 모듈의 검색에 유용하며 모든 구현에 있는 기능은 아닙니다.

2. 버전 선택과 전환

module avail
module load YOUR_COMPILER_MODULE
command -v gcc
gcc --version
module swap YOUR_COMPILER_MODULE YOUR_OTHER_COMPILER_MODULE
module list

CUDA는 제공되는 NVIDIA GPU와 개발 도구가 필요한 경우에만 사용합니다. nvidia-smi의 CUDA 표시와 nvcc --version은 각각 드라이버 지원 수준과 개발 툴킷 정보를 보여주므로 같지 않을 수 있습니다.

module load YOUR_CUDA_MODULE
command -v nvcc
nvcc --version

컴파일러·MPI·수치 라이브러리는 호환되는 조합으로 사용합니다. GNU용 MPI와 다른 컴파일러로 만든 바이너리를 임의로 섞지 않습니다. ANSYS 등 제품이 제공하는 MPI는 제품별 안내를 따릅니다.

3. 환경 변화 확인

printf '%s\n' "$PATH"
printf '%s\n' "${LD_LIBRARY_PATH:-}"
module show YOUR_MODULE
command -v YOUR_COMMAND

module purge는 현재 모듈을 내립니다. Lmod의 sticky 모듈이나 현장 기본값은 남거나 다시 로드될 수 있습니다. module reset의 제공 여부와 기본 모듈도 확인합니다. 알 수 없는 충돌을 해결하려고 사용자 환경 전체를 무조건 삭제하지 않습니다.

4. 실행 스크립트

cat > module-check.sh <<'EOF'
#!/bin/bash
set -euo pipefail
# module 명령이 비대화형 셸에도 제공되는지 확인합니다.
type module
module load YOUR_MODULE
module list
YOUR_COMMAND --version
EOF
bash -n module-check.sh
bash module-check.sh

module이 없으면 관리자가 지정한 초기화 스크립트를 먼저 source합니다. 특정 /etc/profile.d 파일이 모든 현장에 있다고 가정하지 않습니다.

5. 기본 환경과 저장 공간

Lmod에서는 module save YOUR_COLLECTION, module restore YOUR_COLLECTION으로 환경을 저장·복원할 수 있습니다. 이름이 바뀐 모듈은 복원에 실패할 수 있습니다. .bashrc에 모듈을 넣는 경우 기존 파일을 보관하고 승인된 모듈만 추가합니다. 설치되지 않은 CUDA나 특정 버전을 모든 로그인에 강제하지 않습니다.

공유 프로그램을 사용하면 개인 환경의 중복 설치를 줄일 수 있습니다. 개인 사용량은 du -sh "$HOME", 저장소 여유는 df -h "$HOME"로 확인합니다. 사용자 quota는 현장 파일시스템에 맞는 도구·안내를 사용합니다.

Docker가 제공·허용된 노드에서만 사용합니다. 일반 Docker daemon 접근 권한은 root 수준의 권한을 줄 수 있으며 --user는 daemon 접근 권한 자체를 제한하지 않습니다. Docker 그룹 가입, rootless 구성, GPU 실행 권한은 관리자가 정합니다.

1. 사용 환경 확인

docker version
docker info
id

Client만 보이거나 daemon 연결·권한 오류가 나면 담당자에게 문의합니다. /var/run/docker.sock 권한을 넓히거나 승인 없이 sudo로 우회하지 않습니다. Rootless Docker는 별도 구성과 기능 제한이 있습니다.

2. 이미지 선택과 내려받기

IMAGE=YOUR_APPROVED_IMAGE
docker pull "$IMAGE"
docker image ls
docker image inspect "$IMAGE"

프로젝트가 검증한 저장소·태그·가능하면 digest를 기록합니다. latest나 같은 태그의 내용은 바뀔 수 있습니다. 이미지의 OS·CPU·Python·프레임워크·CUDA 버전과 라이선스를 확인합니다. 큰 이미지는 다운로드·로컬 저장 용량을 먼저 확인합니다.

3. 기본 실행과 작업 폴더 연결

현재 폴더를 컨테이너의 /work로 연결합니다. 컨테이너 안에서 호스트의 HOME·사용자명이 자동으로 같은 의미가 되지는 않습니다.

docker run --rm --user "$(id -u):$(id -g)" \
  --mount "type=bind,src=$PWD,dst=/work" -w /work \
  "$IMAGE" python -c 'import sys; print(sys.version)'

이미지가 숫자 UID 실행을 지원해야 합니다. 프로젝트가 추가 그룹이나 쓰기 가능한 HOME을 요구하면 관리자와 이미지 설정을 확인합니다. 입력 전용 경로는 read-only 바인드를 사용할 수 있습니다. 시스템 디렉터리 전체를 임의로 연결하지 않습니다.

docker run --rm --user "$(id -u):$(id -g)" \
  --mount "type=bind,src=$PWD,dst=/work" -w /work \
  "$IMAGE" python /work/your_program.py

--rm은 종료된 컨테이너를 제거하지만 바인드된 작업 폴더의 파일은 남습니다. 컨테이너 내부의 임시 변경은 결과 보관 경로가 아닙니다.

4. 대화형 사용·상태·로그·종료

docker run --name research-shell -it \
  --user "$(id -u):$(id -g)" \
  --mount "type=bind,src=$PWD,dst=/work" -w /work "$IMAGE" sh
docker ps
docker ps -a
docker logs research-shell
docker exec -it research-shell sh
docker stop research-shell
docker rm research-shell

대화형 셸을 나간 다음 같은 컨테이너 이름을 다시 쓰려면 기존 컨테이너를 정리합니다. docker exec는 실행 중인 컨테이너에만 사용합니다. 종료는 본인 컨테이너와 결과 저장을 확인한 뒤 수행합니다. 다른 사용자의 컨테이너를 조작하거나 일괄 prune하지 않습니다.

5. GPU 실행

지원 드라이버와 NVIDIA Container Toolkit이 구성되어 있어야 합니다. 직접 실행이 허용된 환경에서 승인받은 GPU만 지정하는 예제입니다.

docker run --rm --gpus 'device=YOUR_ASSIGNED_GPU_ID' "$IMAGE" nvidia-smi

기존 --runtime=nvidia 방식과 현재 --gpus 방식은 설치 구성에 따라 다릅니다. 과거 예제를 무조건 대체 적용하지 않습니다. Slurm의 CUDA_VISIBLE_DEVICES는 컨테이너/호스트의 GPU 번호와 그대로 대응하지 않을 수 있으므로 스케줄러가 제공하는 컨테이너 연동을 사용합니다. --gpus all로 할당 외 GPU를 사용하지 않습니다.

6. 셸 스크립트로 반복 실행

bash run-container.sh > container-run.log 2>&1

7. 이미지 만들기와 재사용

대화형 변경만 남기기보다 Dockerfile과 환경 파일을 기록합니다. 다음은 별도로 준비한 requirements.txt를 이미지에 추가하는 형태입니다.

FROM YOUR_APPROVED_BASE_IMAGE
WORKDIR /work
COPY requirements.txt /tmp/requirements.txt
RUN python -m pip install --no-cache-dir -r /tmp/requirements.txt

docker build -t local/research-demo:1 .
docker image ls

docker commit은 대화형 컨테이너 변경을 이미지로 만들 수 있으나 이력 재현이 어렵고 비밀정보가 들어갈 수 있습니다. Dockerfile을 우선하고 이미지 레이어에도 비밀값을 넣지 않습니다. 저장소로 배포할 때는 승인된 namespace로 docker tag·docker push하고 인증정보는 이미지에 포함하지 않습니다. 여러 컨테이너 조합은 docker compose가 제공·허용된 경우 별도 프로젝트 설정으로 관리합니다.

8. 정리와 HPC 사용 시 유의점

본인 프로젝트가 사용하지 않는 이미지인지 확인한 뒤 docker image rm YOUR_IMAGE_ID로 정리합니다. 실행 중인 컨테이너와 공유 이미지의 영향을 먼저 확인합니다.

이미지는 노드별 로컬 저장소에 있어야 할 수 있고 RAM 기반 노드에서는 재부팅으로 사라질 수 있습니다. 계산 전에 승인된 방식으로 준비하거나 Apptainer/Singularity의 공유 이미지 방식을 검토합니다. 파일 소유권·메모리·공유 메모리·GPU·네트워크 정책은 현장 설정을 따릅니다.

Apptainer와 Singularity

과학 계산용 컨테이너 실행기입니다. 같은 계열이라도 제품·버전에 따라 옵션과 보안 설정이 다릅니다. 아래 예제는 apptainer를 사용하며 Singularity만 제공되는 현장은 담당자가 확인한 대응 명령으로 바꿉니다.

1. 제공 여부 확인

module avail
command -v apptainer
apptainer --version

모듈 방식이면 현장에서 안내받은 모듈을 먼저 불러옵니다. 컨테이너라고 모든 권한 문제가 사라지는 것은 아닙니다. 호스트 파일·바인드·네트워크·GPU 접근은 사용자 권한과 관리자 정책에 따릅니다.

2. 이미지 가져오기와 기본 실행

apptainer pull research.sif docker://YOUR_APPROVED_IMAGE
ls -lh research.sif
apptainer inspect research.sif
apptainer exec research.sif cat /etc/os-release
apptainer shell research.sif

셸 종료는 exit입니다. 이미지 안에 Python이 있는 경우:

apptainer exec research.sif python --version
apptainer exec --bind "$PWD:/work" --pwd /work research.sif python /work/your_program.py

HOME·현재 폴더 등의 기본 바인드 범위는 버전·설정에 따라 달라집니다. 데이터·출력 경로를 확인하고 명시적으로 연결합니다. 바인드된 호스트 파일은 컨테이너 안에서 변경할 수도 있으므로 필요하면 :ro로 제한합니다.

3. GPU와 공용 라이브러리

apptainer exec --nv research.sif nvidia-smi

GPU 사용이 할당된 노드에서 실행합니다. --nv가 모든 프레임워크·CUDA 조합의 호환성을 보장하지는 않습니다. 이미지의 프레임워크 런타임과 호스트 드라이버 조합을 확인합니다.

관리자가 승인한 공용 라이브러리 경로를 바인드해야 하는 경우의 형태입니다.

apptainer exec --nv --bind YOUR_SHARED_SOFTWARE_PATH:/software:ro \
  research.sif sh -c 'printf "%s\n" "$LD_LIBRARY_PATH"; ls /software'

환경변수를 컨테이너 안에서 확인할 때는 sh -c '...'처럼 셸을 명시합니다. 호스트에서 먼저 확장된 변수값을 보고 컨테이너 내부 값이라고 판단하지 않습니다. 라이브러리 바인드만으로 ABI나 MPI 호환성이 해결되지는 않습니다.

4. 이미지 빌드·수정

SIF 이미지를 직접 수정하지 않는 방식이 일반적이지만, 이미지 생성·수정이 불가능하다는 뜻은 아닙니다. 정의 파일·sandbox·overlay 지원과 권한을 확인합니다.

Bootstrap: docker
From: YOUR_APPROVED_BASE_IMAGE

%post
    echo "Add only approved package-install commands for this image OS."

%runscript
    exec python "$@"

위 형태를 research.def로 저장하고 승인된 빌드 환경에서 생성합니다.

apptainer build research.sif research.def

필요한 권한이나 fakeroot·원격 빌드가 제공되지 않으면 관리자에게 요청합니다. sandbox를 지원하고 수정이 허용된 경우:

apptainer build --sandbox research-sandbox research.sif
apptainer shell --writable research-sandbox
apptainer build research-repacked.sif research-sandbox

--writable이 일반 사용자에게 root 권한을 주지는 않습니다. 영구 변경은 정의 파일에 기록해 재현하고, 동시 쓰기 중인 sandbox를 공유 작업에서 사용하지 않습니다.

5. 실행 스크립트

cat > run-apptainer.sh <<'EOF'
#!/bin/bash
set -euo pipefail
apptainer exec --bind "$PWD:/work" --pwd /work \
  ./research.sif python /work/your_program.py
EOF
bash -n run-apptainer.sh
bash run-apptainer.sh > apptainer-run.log 2>&1

GPU가 필요하면 자원 할당을 먼저 확인하고 --nv를 추가합니다. Slurm에서는 작업 예제의 자원 요청과 함께 사용합니다.

6. Jupyter 실행

Jupyter가 설치된 이미지에서 실행하고 호스트의 작업 폴더를 바인드합니다.

apptainer exec --bind "$PWD:/work" --pwd /work research.sif \
  jupyter lab --no-browser --ip=127.0.0.1 --port=8888

GUI·터널 안내의 SSH 포트 전달로 내 PC 브라우저에서 접속합니다. X11 브라우저 실행이 필수인 것은 아닙니다. 계산 노드에서 실행할 때는 노드 할당과 해당 노드까지의 터널 경로를 확인합니다.

nvidia-smi --query-gpu=index,name,memory.used,memory.total,utilization.gpu --format=csv
printf '%s\n' "${CUDA_VISIBLE_DEVICES:-not-set}"

gpustat은 별도 설치된 경우에만 사용할 수 있습니다. 지속 확인은 watch -n 2 nvidia-smi 또는 nvidia-smi --loop=2를 사용하고 Ctrl+c로 마칩니다. 상태 조회가 자원 예약을 의미하지는 않습니다. 직접 실행 환경에서는 예약·사용 조정 정책을 따릅니다.

2. 작은 TensorFlow GPU 시험

실습 예제를 한 번에 받으려면 Git으로 이 가이드를 내려받을 수 있습니다. 받은 코드를 확인한 뒤 승인된 작업 공간에서 실행하세요.

git clone https://github.com/leekwangseon/openhpc-guide.git
cd openhpc-guide/examples

필요한 파일만 받을 때는 아래 curl 명령을 사용합니다.

검증된 Conda 환경, Module 또는 컨테이너 중 하나를 준비합니다. 예제는 외부 데이터를 내려받지 않는 작은 행렬 계산입니다.

curl -fLO https://leekwangseon.github.io/openhpc-guide/examples/tf-smoke.py

성공하면 TensorFlow 버전·보이는 GPU·실제 장치·체크섬이 출력됩니다. GPU가 없으면 CPU로 조용히 대체하지 않고 실패하도록 구성했습니다. GPU 목록이 비거나 라이브러리 로드가 실패하면 할당·드라이버·런타임 조합을 확인합니다.

3. 짧은 GAN 학습 시험

환경 확인을 위해 합성 데이터를 사용하는 작은 GAN 예제를 제공합니다. 기본 20 step이며 실제 연구용 모델이나 성능 측정용 기준이 아닙니다.

완료하면 현재 작업 폴더에 gan-synthetic-samples.npy가 생성됩니다. GPU가 없는 환경의 짧은 CPU 시험은 --require-gpu를 빼고 자원 정책에 맞게 실행할 수 있습니다. 원본 입력·중요 결과와 별도 실습 폴더를 사용합니다.

Docker의 경우 Docker 안내의 GPU 지정·작업 폴더 바인드를 사용합니다. Slurm 사용 환경에서는 배치 스크립트에 필요한 GPU 요청과 실행 부분을 반영합니다.

5. 오류가 날 때

실제 이미지 데이터의 DCGAN 학습까지 진행하려면 TensorFlow 공식 DCGAN 예제를 참고해 데이터 다운로드 경로·출력·체크포인트·실행 시간을 확인합니다. 본 안내의 작은 합성 데이터 시험을 먼저 통과한 후 같은 환경에서 확장합니다. 기존 TensorFlow 1.x 외부 예제를 사용할 때는 해당 예제의 버전·라이선스·의존성을 검토하고 코드를 확인한 뒤 실행합니다.

증상 확인
GPU를 찾을 수 없음 실제 실행 노드, GPU 배정, CUDA_VISIBLE_DEVICES, 컨테이너 GPU 전달
CUDA 라이브러리 오류 드라이버·프레임워크 런타임 조합, 중복 모듈·경로
Out of memory GPU 실제 사용량, batch 크기, 다른 프로세스, 메모리 할당 정책
no kernel image / unsupported architecture GPU 세대와 해당 바이너리의 지원 범위
GPU 사용률 0% CPU 전처리·입출력 대기·실제 장치 선택·계산 규모

GPU 번호를 임의로 바꾸어 다른 사용자의 자원을 쓰거나 드라이버를 개인 작업으로 교체하지 않습니다. 모델 체크포인트와 환경 버전을 함께 보관하면 재현·복구에 도움이 됩니다.

Slurm을 실제로 사용하는 현장을 위한 안내입니다. 직접 실행이 지정된 현장은 직접 실행 안내를 사용합니다. Slurm 밖에서 시작한 작업은 Slurm 대기열에 자동으로 표시되지 않습니다.

1. 자원과 대기열

Partition은 노드의 논리적 묶음, Job은 자원 요청과 실행 단위입니다. --ntasks는 프로세스 수, --cpus-per-task는 프로세스당 CPU 수입니다. 메모리는 --mem 또는 --mem-per-cpu 등 현장이 사용하는 정책을 확인합니다. 요청량이 크거나 제한을 넘으면 자원이 남아 보여도 작업이 대기할 수 있습니다.

Backfill은 먼저 예정된 작업을 지연시키지 않는 범위에서 빈 시간에 다른 작업을 실행하는 방식입니다. 작업 시작 순서는 단순 제출 순서만이 아니라 예약·파티션·우선순위·필요 자원의 영향을 받습니다.

2. 노드·작업 상태 확인

sinfo
sinfo -Nel
squeue -u "$USER"
squeue -u "$USER" -o '%.18i %.12P %.24j %.8T %.10M %.6D %R'
scontrol show job YOUR_JOB_ID
노드 상태 의미
idle Slurm 기준 미할당. 직접 실행 작업 유무는 별도
mix 일부 자원이 할당된 상태
alloc 자원이 할당된 상태
drain / down 새 작업 배정 제외 / 사용 불가 상태
completing 작업 종료·정리 중
상태 뒤 * 응답하지 않는 노드 표시. 관리자 확인 필요
작업 상태 확인할 점
PENDING %R 또는 Reason 필드의 대기 이유
RUNNING 실행 노드·시간·출력 로그
COMPLETED 종료 코드와 실제 결과를 함께 확인
FAILED / OUT_OF_MEMORY / TIMEOUT 프로그램 오류 / 메모리 / 시간 제한
CANCELLED 사용자 또는 운영 정책에 의한 취소

sinfolong, squeuelong은 표준 Slurm 명령이 아니라 현장별 별칭일 수 있습니다. 없는 경우 위 표준 명령과 출력 형식을 사용합니다.

3. 대화형 작업

srun -p YOUR_PARTITION --nodes=1 --ntasks=1 --cpus-per-task=2 \
  --mem=2G --time=00:10:00 --pty bash
hostname
printf '%s\n' "${SLURM_JOB_ID:-}" "${SLURM_CPUS_PER_TASK:-}"
exit

셸을 열기 전에 자원 배정을 기다릴 수 있습니다. 대화형 셸을 닫아야 자원을 반환합니다. 반면 srun ... hostname처럼 명령을 직접 지정하면 명령이 끝날 때 종료됩니다. 시간 제한은 배정 단계에서 지정합니다.

GPU 노드가 제공되고 해당 파티션에서 GRES를 사용하는 경우 --gres=gpu:1 같은 요청을 추가합니다. GPU 종류·개수 요청 형식은 현장 설정을 따릅니다. 할당 후 nvidia-smi와 프레임워크 GPU 인식을 확인합니다.

4. 첫 배치 작업

공유 작업 폴더에서 파일을 작성합니다. 아래 예제는 2분 안에 호스트명과 날짜를 출력합니다.

cat > hello.slurm <<'EOF'
#!/bin/bash
#SBATCH --job-name=hello
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1
#SBATCH --time=00:02:00
#SBATCH --output=hello-%j.out
#SBATCH --error=hello-%j.err
set -euo pipefail
hostname
date --iso-8601=seconds
EOF
sbatch -p YOUR_PARTITION hello.slurm

Job ID를 기록하고 squeue -u "$USER"로 확인합니다. 완료 후 hello-작업번호.out, .err를 읽습니다. 스크립트의 #SBATCH는 셸 명령이 아니므로 $HOME 같은 셸 변수가 그 위치에서 자동 확장된다고 가정하지 않습니다. %j는 Slurm의 Job ID 치환 표기입니다.

5. Conda·Module·컨테이너 작업 예제

다음 공통 템플릿의 실행 부분에서 사용할 환경 한 가지를 선택합니다. GPU가 필요한 작업에서만 현장에 맞는 GPU 요청을 추가합니다.

cat > research.slurm <<'EOF'
#!/bin/bash
#SBATCH --job-name=research
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=2
#SBATCH --mem=4G
#SBATCH --time=00:10:00
#SBATCH --output=research-%j.out
set -euo pipefail
echo "job=$SLURM_JOB_ID host=$(hostname)"
export OMP_NUM_THREADS="$SLURM_CPUS_PER_TASK"

# Conda 설치 경로와 프로그램을 실제 값으로 변경합니다.
source YOUR_CONDA_ROOT/etc/profile.d/conda.sh
conda activate research-demo
srun python -u ./your_program.py
EOF
sbatch -p YOUR_PARTITION research.slurm

Module을 쓰면 위 Conda 초기화·활성화·실행 부분을 다음으로 바꿉니다. 비대화형 셸의 module 초기화는 현장 절차를 따릅니다.

module load YOUR_MODULE
srun YOUR_APPLICATION YOUR_CONFIRMED_OPTIONS

Apptainer/Singularity를 쓰면 공유 이미지와 작업 폴더를 명시합니다.

srun apptainer exec --bind "$PWD:/work" --pwd /work \
  ./research.sif python /work/your_program.py

GPU가 배정된 작업에는 승인된 이미지 조합에서 --nv를 추가합니다. Docker는 현장의 Slurm 연동 방식과 GPU 장치 매핑을 받아 사용합니다. srun docker run만으로 컨테이너의 권한·자원 격리가 완성된다고 가정하지 않습니다. Docker와 Apptainer 안내를 함께 확인합니다.

6. MPI와 여러 노드

각 노드가 같은 실행파일·라이브러리·입력 경로를 읽을 수 있어야 합니다. 지원되는 MPI 모듈과 Slurm MPI plugin을 확인합니다.

module load YOUR_COMPILER_MODULE YOUR_MPI_MODULE
srun --mpi=list
mpicc -O2 -o mpi-hello mpi-hello.c
srun -p YOUR_PARTITION --nodes=2 --ntasks-per-node=2 \
  --time=00:02:00 --mpi=YOUR_SUPPORTED_PLUGIN ./mpi-hello

예제 소스는 MPI 예제에 있습니다. PMIx/PMI2 등 현장이 지원하는 조합으로 바꾸며, 모든 MPI에 같은 --mpi 값을 적용하지 않습니다. MPI 라이브러리·IB 모듈·응용프로그램을 단계별로 시험합니다. ANSYS와 같은 제품은 제품 자체의 Slurm/MPI 연동 절차를 우선합니다.

7. 작업 취소·로그·실패 진단

scancel YOUR_JOB_ID
scontrol show job YOUR_JOB_ID
tail -n 50 research-YOUR_JOB_ID.out

회계 기능이 구성된 경우:

sacct -j YOUR_JOB_ID --format=JobID,JobName,State,Elapsed,ExitCode,MaxRSS

squeue에서 사라졌다는 사실만으로 성공을 판단하지 않습니다. 메모리 오류는 실제 MaxRSS·요청량·프로세스 수를, TIMEOUT은 시간 제한과 체크포인트를 확인합니다. 무조건 자원을 크게 늘려 재제출하기보다 실패 원인을 먼저 확인합니다.

같은 실행을 여러 입력으로 반복할 때는 현장에서 허용한 Job Array를 사용할 수 있습니다. #SBATCH --array=1-5와 $SLURM_ARRAY_TASK_ID, 출력 이름의 %A_%a를 조합하고 동시 실행 제한과 입력 대응을 확인합니다.

8. 우선순위·시작 예상시간

squeue --start -u "$USER"
sprio -u "$USER"
sshare -l

기능과 권한이 제공되는 경우에 확인합니다. 예상 시작시각은 자원·정책·다른 작업의 종료에 따라 바뀌며 보장된 예약 시각이 아닙니다. Fairshare 정보가 없으면 회계·우선순위 plugin 구성을 담당자에게 확인합니다.

Age, Fairshare, JobSize, Partition, QoS, Association, TRES 등의 요인이 설정된 가중치에 따라 우선순위에 반영될 수 있습니다. 큰 숫자의 우선순위 하나만으로 다음 실행 작업을 결정할 수는 없습니다. 현장의 예약·선점·파티션 정책도 영향을 줍니다.

9. 사용자·그룹·QoS 제한 조회

SlurmDBD와 회계가 설정되어 있고 조회 권한이 있는 경우의 예입니다. 이 안내의 숫자를 운영 제한으로 간주하지 않습니다.

sacctmgr show cluster
sacctmgr show account
sacctmgr show association where user="$USER"
sacctmgr show qos format=Name,Priority,MaxWall,MaxJobsPU,MaxSubmitPU,MaxTRESPU
정책 의미 확인할 값
MaxJobs / MaxJobsPU 동시 실행 수 제한 현장 정책
MaxSubmit / MaxSubmitPU 실행·대기 등을 포함한 제출 수 제한 현장 정책
MaxWall 최대 실행시간 요청 가능 범위
GrpTRES / MaxTRESPU 그룹·사용자의 자원 제한 CPU·메모리·GPU 등
Fairshare / Shares 사용량과 배분 기준 소속 Account·Association
QoS 우선순위·상한·예외 정책 허용된 QoS와 기본값

제한 초과·라이선스 대기·노드 비가용 등 대기 사유를 확인하고 담당자에게 Job ID와 함께 문의합니다. 사용자가 회계·QoS 값을 임의로 수정하지 않습니다.

10. 파티션·노드·설정 확인

scontrol show partition YOUR_PARTITION
scontrol show node YOUR_NODE
scontrol show config

상세 출력의 CPU·메모리·GRES·시간 제한과 현장 안내를 비교합니다. 설정 파일은 /etc/slurm/slurm.conf 등의 현장 경로에 있고 configless 노드는 캐시·서비스 설정이 다를 수 있습니다. 사용자에게 공개되지 않는 값이 있으면 담당자에게 필요한 범위만 요청합니다. 조회와 설정 변경은 다른 권한입니다.

다음은 정책 해석을 위한 가상의 예이며 제공 중인 클러스터의 제한이 아닙니다.

구분 예시 해석
사용자 동시 실행 2개 세 번째 작업은 다른 조건이 충족되어도 대기할 수 있음
프로젝트 동시 GPU 4개 같은 Account 사용자가 함께 사용하는 상한

짧은 작업 QoS 최대 30분 지정 조건을 만족하는 작업만 사용

sbatch --account=YOUR_ACCOUNT --qos=YOUR_QOS -p YOUR_PARTITION job.slurm처럼 승인된 조합을 사용합니다. 정책에 따라 허용된 기본값이 자동 적용될 수도 있습니다. Fairshare 사용량 감소 주기·우선순위 가중치·QoS 제한은 각 현장 값으로 확인합니다.

GUI와 선택 기능

GUI용 X11 전달은 내 PC의 X 서버·서버 설정이 모두 필요합니다. 일반 SSH 접속과 별도 기능입니다. ssh -X를 먼저 사용하고, 신뢰하는 서버에 한해 필요 시 -Y 사용 여부를 관리자에게 확인합니다. 계산 노드까지의 GUI 접속은 승인된 별도 절차를 따릅니다.

Jupyter는 X11을 필수로 요구하지 않습니다. 현장에서 허용한 실행 노드에 서버를 띄우고 SSH 로컬 포트 전달로 브라우저에서 접속할 수 있습니다. 다음은 내 PC에서 실행 노드에 직접 SSH 접속 가능한 경우의 예입니다.

실행 노드에서:

jupyter lab --no-browser --ip=127.0.0.1 --port=8888

내 PC의 별도 터미널에서:

ssh -N -L 127.0.0.1:8888:127.0.0.1:8888 -p YOUR_NODE_SSH_PORT YOUR_USER@YOUR_EXECUTION_HOST

내 PC 브라우저에서 http://127.0.0.1:8888을 열고 서버가 안내한 인증 절차를 따릅니다. 토큰은 공유하지 않습니다. 중계·Slurm 자원 배정이 필요한 현장에는 이 명령을 그대로 적용하지 말고 관리자의 터널·작업 할당 절차를 받습니다. 포트 충돌 시 양쪽 포트와 URL을 함께 조정합니다.

컨테이너는 관리자가 제공·허용한 실행기와 이미지로 사용합니다. Docker 그룹 권한은 일반적인 프로그램 실행 권한보다 강합니다. 그룹 가입을 자동 요청하거나 rootless 구성의 보안 보장을 임의로 가정하지 않습니다. Apptainer/Singularity도 호스트 경로 바인드·네트워크·GPU 접근 정책을 따릅니다.
