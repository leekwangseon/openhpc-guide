OpenHPC 클러스터 사용·운영 가이드

웹에서 읽기 · 오프라인 HTML

사용자와 관리자가 같은 안내서에서 필요한 절차를 찾아볼 수 있도록 구성했습니다. 일반 사용자는 공통 안내와 사용자 안내를, 관리자는 관리자 안내까지 읽습니다.

문서 버전: 1.0 · 검토일: 2026-11-25 · 문서 언어: 한국어

이 문서는 OpenHPC 기반 Linux 클러스터의 범용 안내입니다. OpenHPC는 여러 운영 도구를 묶어 제공하며, 접속·인증·저장소·스케줄러의 실제 구성은 현장마다 다릅니다. 설치 안내서나 특정 제품의 지원 인증을 대신하지 않습니다.

OpenHPC-Guide.html은 위 내용을 합친 오프라인 열람·인쇄용 파일입니다. 사용자 안내와 관리자 안내를 탭으로 골라 볼 수 있습니다. Markdown 파일은 GitHub 게시·버전 관리용 원본입니다.

현장 적용 전 관리자 확인

  • 현장별 안내서에서 접속 주소·포트·개인 계정 발급 방법을 채웁니다. 비밀번호·비밀키·라이선스 원문은 넣지 않습니다.
  • 운영 방식을 직접 실행 / Slurm 사용 / 혼합 운영 중 하나로 명시합니다. Slurm이 설치되어 있다는 사실과 사용 의무는 다릅니다.
  • CPU 전용·GPU 유무, IB 유무, 제공 프로그램·모듈·버전을 확인합니다. 없는 기능은 사용자에게 제공되는 기능으로 표시하지 않습니다.
  • 관리자 예제는 배포 도구 버전을 확인한 뒤 적용합니다. Warewulf 3의 wwsh, wwvnfs 절차를 Warewulf 4의 wwctl 절차와 혼용하지 않습니다.
  • 사용자 계정으로 첫 접속·공유 경로 쓰기·간단한 계산·결과 회수를 시험합니다. 관리자 접속 성공만으로 사용자 검증을 대신하지 않습니다.

예제 읽는 법

명령에는 프롬프트 표시를 넣지 않았습니다. 코드 블록의 명령만 복사합니다. YOUR_* 값은 현장 안내서에 맞게 바꾼 뒤 실행합니다. 값을 모르면 관리자에게 문의합니다.

명령 앞 설명의 실행 위치를 확인합니다. 내 PC, 로그인 노드, 계산 노드, 관리 노드는 서로 다를 수 있습니다. 한 서버가 여러 역할을 겸할 수도 있습니다.

관리자 안내가 공개되어 있어도 일반 사용자에게 관리자 권한이 부여되는 것은 아닙니다. 실제 접속 권한과 운영 변경 권한은 현장 정책을 따릅니다.

공통 안내

1. 클러스터의 역할

클러스터는 여러 서버를 함께 관리하고 계산에 사용하는 환경입니다. 프로그램이 병렬 실행을 지원하고 적절하게 설정되어야 여러 서버를 한 계산에 활용할 수 있습니다. 서버가 여러 대라는 이유만으로 프로그램이 자동 분산되지는 않습니다.

구성 요소 하는 일 사용자가 알아둘 점
로그인 노드 접속, 파일 준비, 프로그램 실행 준비 장시간 계산 허용 여부는 현장 정책 확인
관리 노드 사용자·부팅 이미지·내부망·서비스 관리 일반 사용자가 설정을 바꾸지 않음
계산 노드 실제 계산 실행 배정 또는 예약받은 자원 범위 사용
공유 저장소 여러 노드에서 같은 파일 제공 경로·권한·백업 정책 확인
관리망 부팅, 관리, 일반 통신 사용자 PC에서 직접 접근되지 않을 수 있음
고속망 IB 등 병렬 통신 응용프로그램의 MPI·통신 설정도 필요
스케줄러 작업 자원 배정과 대기열 관리 설치 여부와 실제 사용 방식은 별도 확인

관리 노드와 로그인 노드가 같은 장비일 수 있습니다. BMC는 운영체제와 별개로 전원·하드웨어 상태를 관리하는 인터페이스이며 관리자 영역입니다.

2. 운영 방식 선택

방식 작업을 시작하는 방법 사용 전 확인
직접 실행 승인된 노드 또는 제품의 실행 도구에서 시작 사용할 노드, 코어·메모리, 시간, 예약·조정 방법
Slurm 사용 sbatch, srun 등으로 자원 요청 파티션, 자원 요청량, 시간 제한
혼합 운영 승인된 범위에서 직접 실행과 Slurm 병행 노드·시간대 분리 등 관리자 정책

직접 실행한 작업은 Slurm의 작업 목록에 자동 등록되지 않습니다. 따라서 squeue가 비어 있거나 sinfo가 idle이라고 해서 노드가 실제로 비어 있다는 뜻은 아닙니다. 혼합 운영은 사용 범위와 자원 중복 방지 방법을 정한 뒤 시행합니다.

3. 파일은 어디에 저장하나요?

아래 경로는 흔한 예시입니다. 실제 공유 여부와 정책은 현장 안내서를 우선합니다.

위치 예시 일반적인 용도 주의할 점
/home/사용자명 개인 설정, 소스, 작은 작업 파일 용량 제한·공유 여부 확인
/data 또는 프로젝트 경로 입력·결과·공동 작업 데이터 사용자가 쓸 수 있는 하위 경로 사용
/opt/ohpc/pub 관리자가 설치한 공용 프로그램 일반 사용자는 보통 읽기·실행만 가능
계산 노드의 /tmp·로컬 scratch 임시·중간 계산 파일 재부팅·정리 시 삭제될 수 있으므로 결과 회수
계산 노드의 RAM 루트 stateless 노드의 OS·임시 변경 개별 설치·설정이 재부팅 때 사라질 수 있음

공유 저장소, RAID, 백업은 서로 다른 기능입니다. 파일이 여러 노드에서 보이거나 RAID로 구성되어 있어도 삭제·오염·장애에 대비한 별도 백업이 있다는 뜻은 아닙니다. 백업 대상, 주기, 보관 기간, 복구 요청 방법을 관리자에게 확인합니다.

4. 공통 사용 수칙

  • 개인 계정을 사용합니다. 다른 사용자의 계정·SSH 키를 함께 쓰지 않습니다.
  • 비밀번호·비밀키·라이선스 원문을 메일 본문, 공개 저장소, 오류 화면에 포함하지 않습니다.
  • 승인된 자원만 사용합니다. 다른 사용자의 프로세스·파일을 임의로 종료·수정하지 않습니다.
  • 관리자 승인 없이 재부팅·전원 조작·마운트 변경·시스템 패키지 변경을 하지 않습니다.
  • 공유 폴더에 chmod -R 777을 적용해 권한 문제를 해결하지 않습니다. 필요한 사용자·그룹 권한을 요청합니다.
  • 큰 파일 전송·대규모 파일 탐색·환경 설치도 저장소와 네트워크에 부하를 줄 수 있습니다. 현장 운영 정책을 따릅니다.

용어 뜻

CPU 사용량, 메모리, 디스크 여유 공간, 라이선스는 각각 별도의 제약입니다. CPU가 남아 있어도 메모리나 라이선스가 부족하면 계산이 실패할 수 있습니다.

사용자 안내

1. 처음 사용하는 순서

  1. 현장 안내서에서 운영 방식·접속 주소·개인 계정을 확인합니다.
  2. 로그인 노드에 접속하고 hostname, whoami로 접속 대상을 확인합니다.
  3. 관리자에게 지정받은 공유 경로에 작업 폴더를 만듭니다.
  4. 사용할 노드·CPU·메모리·실행 시간을 배정 또는 예약받습니다.
  5. 승인된 프로그램과 실행 환경을 불러오고 작은 시험 계산부터 실행합니다.
  6. 로그와 자원 사용을 확인하고, 완료 결과를 보존 경로로 회수합니다.

2. 접속하기

내 PC에서 실행

Windows는 PowerShell/OpenSSH 또는 조직에서 허용한 SSH 클라이언트를, macOS·Linux는 터미널을 사용할 수 있습니다. 클라이언트별 기능·라이선스는 해당 배포처에서 확인합니다.

ssh -p YOUR_SSH_PORT YOUR_USER@YOUR_LOGIN_HOST

처음 접속할 때 표시되는 호스트 키 지문은 관리자에게 받은 지문과 비교합니다. 호스트 키가 변경되었다는 경고가 나오면 재설치·교체 여부를 확인합니다. 경고를 우회하거나 기존 키를 무조건 삭제하지 않습니다.

비밀번호 입력 중 화면에 글자가 보이지 않는 것은 정상입니다. 비밀번호·다중 인증·키 인증 중 현장에서 지정한 방법을 사용합니다.

중계 서버·VPN이 필요한 현장에서는 관리자에게 받은 전용 접속 절차를 사용합니다. 중계 서버의 127.0.0.1과 내 PC의 127.0.0.1은 다른 대상입니다. 리버스 유지보수 통로를 일반 사용자 접속 경로로 임의 사용하지 않습니다.

접속한 서버에서 확인

hostname
whoami
pwd

현장 안내서의 로그인 노드 이름과 개인 계정이 표시되는지 확인합니다. 계산 노드 접속이 별도로 필요한 경우에만 승인된 방식으로 이동합니다.

3. 작업 폴더와 파일 전송

다음 예제는 HOME이 작업에 허용된 공유 경로일 때만 사용합니다. 별도 프로젝트 경로가 있으면 그 경로에서 시작합니다.

mkdir -p "$HOME/work/first-test"
cd "$HOME/work/first-test"
pwd
df -h .

내 PC에서 작은 파일을 올리는 예제입니다. YOUR_USER_HOME은 /home/개인계정 등 관리자가 안내한 절대 경로로 바꿉니다.

scp -P YOUR_SSH_PORT ./input.dat YOUR_USER@YOUR_LOGIN_HOST:YOUR_USER_HOME/work/first-test/

결과를 내 PC의 현재 폴더로 내려받습니다.

scp -P YOUR_SSH_PORT YOUR_USER@YOUR_LOGIN_HOST:YOUR_USER_HOME/work/first-test/result.dat ./

SSH는 소문자 -p, SCP는 대문자 -P로 포트를 지정합니다. GUI 파일 전송에서는 SFTP를 선택하고 같은 주소·계정·SSH 포트를 사용합니다. 중계 접속이면 별도 SFTP 중계 설정이 필요할 수 있습니다.

대용량·다수 파일은 양쪽에 rsync가 제공될 때 사용할 수 있습니다. 재실행 시 이미 전송된 내용을 활용하며 --partial은 중단된 부분 파일을 보관합니다. 대상 경로와 덮어쓰기 여부를 먼저 확인합니다.

rsync -av --partial --progress -e 'ssh -p YOUR_SSH_PORT' ./inputs/ YOUR_USER@YOUR_LOGIN_HOST:YOUR_USER_HOME/work/first-test/inputs/

이 예제에는 파일 삭제 옵션을 넣지 않았습니다. 중요한 결과는 현장 백업·보관 정책에 따라 별도 보존합니다.

4. 실행 환경 불러오기

Module이 제공되는 현장에서만 사용합니다.

module list
module avail
module show YOUR_MODULE
module load YOUR_MODULE

YOUR_MODULE은 실제 목록에 있는 프로그램/버전으로 바꿉니다. 작업 기록에 프로그램 버전과 모듈 목록을 남깁니다. module purge는 현재 환경을 모두 내리므로 실행 중인 작업의 환경 설정을 임의로 바꾸지 않습니다.

Conda·Python·컨테이너는 제공되는 경우에만 사용합니다. 오래된 예제의 Python·CUDA·딥러닝 버전을 그대로 설치하지 말고 프로젝트 요구 버전과 지원 조합을 확인합니다. 시스템 Python을 덮어쓰거나 일반 사용자 작업에 sudo pip를 사용하지 않습니다.

5. 직접 실행하는 현장

이 절차는 스케줄러를 통하지 않는 실행이 허용되고 노드 직접 접속 권한이 제공된 경우에만 적용합니다. ANSYS 등 제품 자체의 원격 실행 도구를 사용하는 현장은 제품별 안내를 우선합니다.

실행 전

관리자 또는 예약 체계에서 사용할 노드·CPU·메모리·종료 시각을 확인합니다. 아래 명령은 상황을 보는 보조 수단이며 예약이나 자원 점유권을 보장하지 않습니다.

ssh YOUR_APPROVED_NODE
hostname
uptime
free -h
ps -u "$USER" -o pid,etime,%cpu,%mem,args

w는 로그인 세션을 보여줄 뿐, 모든 계산 작업을 보여주지는 않습니다. 다른 사람이 로그인하지 않았어도 계산 중일 수 있습니다. GPU 확인 명령은 해당 GPU와 도구가 설치된 노드에서만 사용합니다.

계산 시작

지정한 공유 작업 폴더에서 제품별 안내 명령으로 실행합니다. 다음은 문법 설명용이며 실제 실행 명령이 아닙니다.

YOUR_APPLICATION YOUR_CONFIRMED_OPTIONS > run.log 2>&1

코어 수·MPI 방식·노드 목록·메모리 옵션은 프로그램별로 다릅니다. 단일 노드 계산 성공 후 멀티노드 계산을 시험합니다. 여러 노드에서 같은 파일을 동시에 덮어쓰지 않도록 작업 폴더와 출력 파일을 분리합니다.

ANSYS의 경우 제품·버전·실행 경로·라이선스 서버·HPC 사용 권한·MPI/IB 설정을 설치 담당자에게 확인합니다. 클러스터의 일반 OpenMPI 모듈을 ANSYS용 MPI로 자동 지정하지 않습니다.

접속 종료 후에도 유지해야 하는 작업

현장에서 tmux 사용을 허용하고 설치한 경우의 예입니다. 프로그램을 실행할 계산 노드에서 시작합니다.

tmux new -s first-test

세션 안에서 계산을 시작합니다. Ctrl+b를 누른 뒤 d를 누르면 세션에서 분리됩니다. 같은 노드·같은 계정으로 돌아와 다시 연결합니다.

tmux attach -t first-test

tmux는 노드 재부팅·장애를 견디는 작업 관리자가 아니며, 현장의 로그아웃 정리 정책에 따라 유지되지 않을 수 있습니다. 긴 계산에는 프로그램의 체크포인트 기능과 승인된 실행 방식을 확인합니다.

진행 확인과 중지

다른 접속 세션에서도 작업이 실행되는 같은 노드·같은 경로에서 확인합니다.

tail -n 50 run.log
tail -f run.log

tail -f는 Ctrl+c로 종료해도 계산이 중단되지 않습니다. 계산 자체는 제품의 정상 종료·체크포인트 저장 기능을 먼저 사용합니다. 프로세스를 종료해야 하면 본인 PID와 작업을 확인한 뒤 kill -TERM PID를 사용합니다. MPI 작업은 여러 프로세스를 만들 수 있으므로 실행기 또는 제품이 안내한 종료 방법을 따릅니다. killall, 다른 사용자의 PID, 강제 종료를 일반 절차로 사용하지 않습니다.

6. Slurm을 사용하는 현장만

Slurm을 사용하지 않는 현장은 이 절을 건너뜁니다. 파티션·제한 정책은 현장 안내서에 따릅니다.

sinfo
squeue -u "$USER"

첫 배치 작업은 계산하지 않는 작은 시험으로 시작합니다. 로그인 노드의 공유 작업 폴더에서 다음 파일을 만듭니다.

cat > hello.slurm <<'EOF'
#!/bin/bash
#SBATCH --job-name=hello
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1
#SBATCH --time=00:02:00
#SBATCH --output=hello-%j.out
hostname
date
EOF
sbatch -p YOUR_PARTITION hello.slurm

제출 응답의 Job ID를 기록하고 squeue -u "$USER"로 확인합니다. 완료 후 현재 폴더의 hello-작업번호.out을 확인합니다. 취소는 scancel YOUR_JOB_ID를 사용합니다.

srun hostname 같은 명령은 실행할 명령이 끝나면 종료됩니다. srun --pty bash로 대화형 셸을 시작한 경우 셸을 exit로 끝내야 합니다. 작업 목록에서 사라졌다는 것만으로 계산 성공을 판단하지 말고 출력·오류 로그와 결과를 확인합니다. sacct는 회계 기능이 구성된 경우에 사용합니다.

7. GUI·Jupyter·컨테이너: 제공되는 경우만

GUI용 X11 전달은 내 PC의 X 서버·서버 설정이 모두 필요합니다. 일반 SSH 접속과 별도 기능입니다. ssh -X를 먼저 사용하고, 신뢰하는 서버에 한해 필요 시 -Y 사용 여부를 관리자에게 확인합니다. 계산 노드까지의 GUI 접속은 승인된 별도 절차를 따릅니다.

Jupyter는 X11을 필수로 요구하지 않습니다. 현장에서 허용한 실행 노드에 서버를 띄우고 SSH 로컬 포트 전달로 브라우저에서 접속할 수 있습니다. 다음은 내 PC에서 실행 노드에 직접 SSH 접속 가능한 경우의 예입니다.

실행 노드에서:

jupyter lab --no-browser --ip=127.0.0.1 --port=8888

내 PC의 별도 터미널에서:

ssh -N -L 127.0.0.1:8888:127.0.0.1:8888 -p YOUR_NODE_SSH_PORT YOUR_USER@YOUR_EXECUTION_HOST

내 PC 브라우저에서 http://127.0.0.1:8888을 열고 서버가 안내한 인증 절차를 따릅니다. 토큰은 공유하지 않습니다. 중계·Slurm 자원 배정이 필요한 현장에는 이 명령을 그대로 적용하지 말고 관리자의 터널·작업 할당 절차를 받습니다. 포트 충돌 시 양쪽 포트와 URL을 함께 조정합니다.

컨테이너는 관리자가 제공·허용한 실행기와 이미지로 사용합니다. Docker 그룹 권한은 일반적인 프로그램 실행 권한보다 강합니다. 그룹 가입을 자동 요청하거나 rootless 구성의 보안 보장을 임의로 가정하지 않습니다. Apptainer/Singularity도 호스트 경로 바인드·네트워크·GPU 접근 정책을 따릅니다.

관리자 안내

이 절은 운영 변경 권한이 있는 관리자를 위한 절차입니다. 명령은 Linux·배포 도구·현장 정책에 따라 달라집니다. 사용자 안내의 직접 실행·Slurm 운영 구분을 먼저 확인합니다.

1. 인수 시 구성표

관리자용 현장 기록에는 OS·OpenHPC·Warewulf·커널·스케줄러 버전, 역할별 서버명, 노드의 관리망·고속망·MAC·BMC, 디스크·마운트·공유 경로, 인증 방식, 서비스 의존 관계를 기록합니다.

공개 문서에는 실제 고객의 주소·호스트명·MAC·장비 일련번호·SSH 지문·구성 보관본을 넣지 않습니다. 내부 구성표는 접근 권한을 제한하고 비밀키·비밀번호는 별도 비밀 관리 수단에 보관합니다.

운영 정책에는 다음을 포함합니다.

  • 직접 실행 / 스케줄러 / 혼합 운영 중 사용할 방식
  • 노드 예약·최대 CPU·메모리·GPU·작업 시간·로그아웃 후 작업 정책
  • 계정 신청·승인·만료·퇴사 처리와 문의 담당자
  • 데이터 소유자, 용량·quota, 보존·정리·백업·복구 책임
  • 점검 시간, 서비스 공지, 장애 등급과 복구 연락 체계

2. 일상 점검

아래는 읽기 전용 진단 예제입니다. 존재하는 서비스·인터페이스에만 적용합니다. 출력에는 사용자명·경로 등이 포함될 수 있으므로 외부 공개 전 확인합니다.

hostname
date --iso-8601=seconds
uptime
df -hT
findmnt -t nfs,nfs4
systemctl --failed
ip -br addr
대상 확인 예시 정상 여부 판단
SSH·인증 지정 SSH 서비스, 계정별 로그인 시험 일반 사용자로 승인된 경로에 접속 가능
NFS exportfs -v, 클라이언트 findmnt 허용 대상·경로·읽기/쓰기·root_squash 일치
배포 노드 등록, DHCP/TFTP/HTTP 로그 지정 MAC/IP가 올바른 이미지로 부팅
IB ibstat, rdma link, SM 서비스 예상 링크 상태·속도, 실제 통신 시험
Slurm 사용 시 sinfo -Nel, squeue, 관련 서비스 노드 상태와 시험 작업 결과 일치
하드웨어 BMC 상태·이벤트·센서 현재 오류와 과거 누적 이벤트를 구분
저장소 사용률·inode·quota·오류 로그 현장 경보 기준과 비교, 증가 추세 확인

서비스의 정확한 이름과 로그 위치는 현장 구성표에 적습니다. Active나 링크 속도만으로 정상이라고 판단하지 말고, 사용자 인증·저장소 접근·작은 계산을 이어서 검증합니다. ib_write_bw 같은 부하 시험은 영향 범위를 확인한 점검 시간에 실시합니다.

3. 사용자 계정 관리

추가

  1. 소속·책임자·사용 기간·프로젝트·필요 권한을 승인받습니다.
  2. 로컬 계정 또는 LDAP/AD 등 실제 인증 체계를 확인합니다. 클러스터 전체 UID/GID 충돌을 검사합니다.
  3. 승인된 계정과 홈·프로젝트 디렉터리를 생성하고 초기 인증 정보를 별도 전달합니다.
  4. 공유 저장소 소유권·그룹·quota와 노드 인증을 구성합니다.
  5. 이미지 기반 구성이라면 계정 매핑을 영구 이미지 또는 관리되는 배포 파일에 반영합니다.
  6. 해당 사용자로 로그인·노드 접근·공유 경로 쓰기·프로그램 실행을 시험하고 결과를 기록합니다.

사용자 비밀번호를 명령 인수·셸 이력·공개 스크립트에 기록하지 않습니다. 마스터의 /etc/shadow, /etc/gshadow, 개인 SSH 비밀키를 통째로 계산 노드에 복사하는 것을 기본 절차로 사용하지 않습니다. 인증·파일 배포 대상은 버전별로 명시하고 시스템 서비스 계정 UID/GID와의 호환성을 확인합니다.

비활성화와 제거

먼저 계정 잠금·SSH 키·디렉터리 서비스·스케줄러 권한 등 모든 인증 경로를 검토합니다. 비밀번호 잠금만으로 키 로그인이 차단되는지 단정하지 않습니다. 실행 중인 직접 작업과 스케줄러 작업, 파일 소유권·공동 연구 영향을 확인합니다.

홈·프로젝트 데이터는 소유자와 보존 정책을 확인한 뒤 처리합니다. 계정 제거와 데이터 삭제는 별도 승인·기록 대상으로 분리합니다. 범용 가이드에 계정 제거 직후의 재귀 삭제 명령을 넣지 않습니다.

4. 프로그램과 OS 라이브러리 변경

저장 위치를 먼저 선택

설치 대상 반영 위치 확인 사항
공용 응용프로그램 모든 노드가 같은 경로로 읽는 공유 트리 실행 권한, 라이선스, Module, MPI 호환
OS 런타임 라이브러리 영구 계산 노드 이미지 및 필요한 관리·로그인 노드 RPM 의존성·동적 로드·재부팅 검증
개인 Python 환경 허용된 사용자 경로 용량·재현 파일·지원 정책
GPU 드라이버·커널·RDMA 검증된 커널·드라이버·부팅 이미지 조합 설치본 지원 범위, 대표 노드 시험

공유 응용프로그램이 보이더라도 필요한 OS 라이브러리가 노드마다 없으면 실행되지 않습니다. 반대로 RAM 기반 노드에서만 변경한 설정은 재부팅 후 사라질 수 있습니다.

공통 변경 순서

  1. 변경 이유·영향 노드·예상 중단 시간·복구 조건을 기록합니다.
  2. 변경할 설정과 이미지의 이전 버전 및 현장에서 승인한 범위를 보관합니다. 설정 보관과 사용자 데이터·전체 이미지 백업을 구분합니다.
  3. 현장의 배포 도구 버전을 확인하고 영구 구성을 수정합니다.
  4. 이미지 생성 성공과 노드 할당 상태를 확인합니다. 실패한 이미지를 배포하지 않습니다.
  5. 시험 노드의 작업을 비우고 새 작업 유입을 막은 뒤 정상 재부팅합니다.
  6. OS·커널·네트워크·인증·마운트·라이브러리·응용프로그램을 확인합니다.
  7. 작은 단일 노드 작업, 필요 시 멀티노드·IB·라이선스 시험을 수행합니다.
  8. 성공한 구성만 나머지 노드로 확대하고 사용자 안내·구성표를 갱신합니다.

Warewulf 3 + Enterprise Linux 8 예제에 한정

다음은 버전이 확인된 Warewulf 3의 기존 이미지에 승인된 패키지를 추가하는 형태입니다. YOUR_*을 실제 값으로 바꾸고 이미지 경로·저장소를 확인합니다.

IMAGE=/YOUR_CONFIRMED_IMAGE_PATH
test -d "$IMAGE/etc"
dnf --installroot="$IMAGE" --releasever=8 install YOUR_APPROVED_PACKAGE
wwvnfs --chroot="$IMAGE"

성공 여부를 단계마다 확인하고 실패 시 다음 단계로 진행하지 않습니다. 이 예제는 노드 재부팅을 자동 실행하지 않습니다. 이미지 경로를 확인하지 않은 상태에서 적용하거나 인증·SELinux 문제를 피하려고 보안 설정을 일괄 해제하지 않습니다.

Warewulf 4는 wwctl을 사용하며 이미지·프로파일·overlay 관리 방식이 다릅니다. 설치된 버전의 공식 절차로 별도 운영서를 작성합니다. 실행 중 노드에 패키지 관리자가 없는 구성에서는 이미지 갱신과 계획된 재부팅으로 적용할 수 있습니다.

5. NFS와 권한

공유 대상은 필요한 호스트 또는 관리망으로 제한합니다. 기본 예제에 전체 허용 * 또는 no_root_squash를 사용하지 않습니다. NFS 접근 제한은 암호화·사용자 인증을 모두 대신하지 않으므로 망 격리·방화벽·인증 정책도 함께 확인합니다.

아래 IP는 문서 예시용 주소이며 실제 서비스 주소가 아닙니다.

/srv/projects 192.0.2.21(rw,sync,root_squash,no_subtree_check)

exports 수정 전 기존 설정을 보관하고 경로·대상·소유권·마운트 상태를 확인합니다. 승인된 변경 후 exportfs -ra, exportfs -v로 적용·검증합니다. 재시작이 필요한지는 서비스와 변경 내용을 기준으로 판단합니다.

클라이언트 마운트는 영구 이미지·overlay·구성 관리에 반영합니다. 사용하는 NFS 버전과 _netdev 등 부팅 의존성을 현장에서 검증합니다. 특정 파일시스템용 quota 명령을 모든 현장에 적용하지 않습니다. 사용자 계정으로 쓰기·그룹 공유를 시험하며 root_squash 때문에 실패한 root 쓰기를 이유 없이 예외 처리하지 않습니다.

6. 재부팅·정지와 혼합 운영

직접 실행 환경에서는 사용자 예약 기록과 실제 프로세스·응용프로그램 상태를 확인해야 합니다. w 또는 Slurm 작업 목록 하나만으로 작업이 없다고 판단하지 않습니다.

Slurm을 사용하는 노드는 DRAIN 등 현장 절차로 새 작업을 차단하고 기존 작업을 정상 종료시킵니다. 직접 작업이 같은 노드에 있다면 별도로 확인합니다. 검증 후에만 노드를 다시 가용 상태로 전환합니다.

정상 종료·재부팅을 우선하며, 강제 전원 조작은 OS 응답·저장소 쓰기·업무 영향·승인을 확인한 장애 절차로 수행합니다. BMC 전원 On은 OS 부팅 성공을 의미하지 않습니다.

전체 정지·기동 순서는 저장소·관리/로그인 노드·계산 노드의 의존 관계에 맞춰 현장 운영서에 적습니다. 모든 현장에 같은 전원 순서를 복사하지 않습니다. 정전 후에는 공유 저장소와 핵심 서비스가 준비된 뒤 계산 노드의 마운트·인증·작업을 확인합니다.

혼합 운영은 직접 실행용과 스케줄러용 노드·시간대를 분리하는 등의 정책을 명시합니다. 직접 작업이 사용하는 자원을 Slurm이 자동 예약·제한한다고 가정하지 않습니다.

8. 운영 보안과 복구

관리 권한은 개인 계정과 필요한 sudo 범위로 제공합니다. 유지보수 SSH 키는 전용으로 발급하고 권한·보관·만료·회수 절차를 정합니다. 중계 터널 수신 주소·포트·접근 계정을 제한하고 서비스 자동 시작·재접속과 복구 경로를 점검합니다. 고객별 터널·BMC 접속 정보를 공개 저장소에 보관하지 않습니다.

Munge 키 등 클러스터 공통 비밀은 소유자·파일 모드·배포 대상·교체 절차를 제한합니다. 공개 가이드에는 키 값·실제 설정 보관본을 포함하지 않습니다. Docker 그룹, privileged 컨테이너, 호스트 경로 바인드는 별도 권한 검토 대상입니다.

설정·메타데이터·사용자 데이터·이미지의 백업 범위는 각각 정의합니다. 복구 순서와 복구 시험 결과, 마지막 정상 구성·검증일을 기록합니다. 보관본에 인증 정보가 포함되면 암호화·접근 제한·보관 기간을 적용합니다.
